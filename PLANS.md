## 11. Implemented readability-and-integrity boundary

The implemented transition consumes `ProductionReadOnlyDatabaseConnection` and performs exactly this sequence on its same privately owned connection: run `PRAGMA cipher_integrity_check`; require normal end-of-stream with zero rows; run `PRAGMA main.quick_check(1)`; require exactly one SQLite `TEXT` row whose complete value is exactly `ok`; require normal end-of-stream after that row; and return a new opaque readability-and-integrity-validated production connection owner. No separate readability query exists. This stage does not read `sqlite_master`, metadata tables, `application_id`, `user_version`, product tables, or arbitrary content, and it exposes no unrestricted SQL.

Success is represented only by possession of the new opaque validated owner. The consuming transition retains the same `rusqlite::Connection`, `ConnectionLifetimeWriteGuard`, and `InspectedProductionDatabaseFile` lifetime unit. The validated owner exposes only consuming explicit close and later separately approved fixed consuming transitions. It establishes no metadata table existence, metadata row validity, SQLite `application_id`, SQLite `user_version`, schema-contract validity, database/evidence correspondence, freshness, startup/setup authority, migration authority, recovery authority, backup/restore authority, or operational database use.

The canonical coarse validation categories are `EncryptedDatabaseAuthenticationOrCipherIntegrityFailed`, `SQLiteReadabilityOrIntegrityFailed`, `ValidationUnavailable`, and `ValidationInterruptedOrIncomplete`. The first returned cipher diagnostic row establishes failure; its text is not decoded, copied, formatted, retained, or logged, and later diagnostic rows need not be consumed. The row stream must be dropped or reset before close. Cipher success requires normal zero-row completion. Quick-check success requires exactly the one complete text value `ok` and normal completion; zero rows, multiple rows, non-text output, non-`ok` output, stepping errors, interruption, malformed shape, or premature termination fail closed. `quick_check` is not full `integrity_check` and proves only its limited SQLite invariants.

No active cancellation API or rusqlite hooks feature is part of this stage. No validation succeeds without its complete required terminal result; interruption, statement failure, malformed result shape, or premature termination maps to a coarse fail-closed result. Both operations run sequentially on the same connection while the existing guard and inspection proof remain retained and query-only, defensive mode, and read-only opening remain active. No explicit SQLite transaction is added, and no stronger snapshot guarantee is claimed beyond that guarded same-connection lifetime.

On validation failure, explicit close is attempted after the row stream and statement are released. Close success returns the primary coarse validation category. Close failure preserves that already determined category together with an opaque close-retry owner containing the complete connection, guard, and inspection-proof lifetime unit. Neither validation nor close outcomes retain or expose SQL or PRAGMA text, result diagnostics, paths, keys, identifiers or identities, SQLite/native codes, raw handles, or rusqlite errors or chains.

Carlo accepts that `cipher_integrity_check` may synchronously scan the whole file with work proportional to database pages. This stage introduces no production database-size ceiling and makes no bounded-latency or active-cancellation claim. The accepted lifecycle runs it on the blocking startup worker rather than the UI/event loop; this does not bound worker duration or eliminate shutdown drain time.

## 12. Implemented live metadata and SQLite-header validation boundary

The implemented consuming transition starts from `ReadabilityAndIntegrityValidatedProductionDatabaseConnection` and performs only this first-failed-stage sequence: prepare and fully observe `PRAGMA main.application_id`; require one result column, exactly one row, SQLite `INTEGER`, signed-32-bit representability, and normal terminal completion; compare with `0x43484150` and fail immediately with `WrongApplicationId` on mismatch; then apply the same strict shape policy to `PRAGMA main.user_version` and retain that value temporarily. It next prepares and executes exactly this fixed query:

```sql
SELECT
    singleton_id,
    metadata_contract_version,
    database_schema_version,
    permanent_application_identifier,
    database_format_identity,
    parish_identifier,
    installation_identifier,
    installation_generation,
    recovery_replacement_generation,
    database_key_generation_identifier,
    setup_publication_identifier,
    database_created_at
FROM main.church_app_database_metadata
LIMIT 2
```

The statement must expose exactly 12 result columns. Normal zero-row completion is `MetadataRowMissing`. The first row's values are copied into a private owned raw observation before stepping again. ## 24. Locked Rust-owned migration-confirmation construction boundary

Rust must establish an exact pending production-database-migration confirmation opportunity before the frontend can confirm or cancel anything. The frontend cannot create that opportunity, supply its identity, or create authority. A bare confirmation call without Rust-owned pending context is insufficient and must never authorize migration. The opportunity is process-local Rust state. Its approved owner direction is `ApplicationLifecycle`, or a migration-specific substate owned beneath it, because that lifecycle already retains privileged Rust owners, serializes transitions under a mutex, and handles shutdown races without exposing those owners through IPC. `StartupStatus` must not carry migration-confirmation authority state, and no generic maintenance state machine is approved.

The conceptual one-shot progression is `NotOffered -> Pending -> Authorized -> Consumed`, with `Pending -> Revoked`. Confirmation must atomically consume `Pending` and directly construct and internally retain the future `ProductionDatabaseMigrationAuthorization`; cancellation is non-authorizing and must atomically move `Pending` to terminal `Revoked`. `Authorized`, `Consumed`, and `Revoked` are terminal for the current process. Once an opportunity is confirmed, cancelled, revoked, invalidated, or consumed, Rust must not create another `Pending` opportunity in that process. A fresh application process is required before another opportunity may exist. This no-renewal rule prevents a stale or queued frontend invocation from confirming a later opportunity. Restart destroys every pending opportunity and every unconsumed authorization because both are process-local, non-persistent, and non-renewing.

Shutdown must revoke `Pending` before, or atomically with, entering stopping or shutdown state. A migration-context or eligibility invalidation detected by the future Rust owner must also revoke `Pending`. Eligibility is not part of this confirmation boundary and must be independently revalidated when migration execution is later composed. Source and target versions, backup proof, full-integrity proof, writable ownership, exclusivity, installation/evidence/freshness state, and version eligibility remain separate prerequisites and are not command inputs or fields of the authorization identity.

The approved future authority-changing command direction is the migration-specific, argument-free `confirm_production_database_migration`, whose sole conceptual input is Tauri-managed Rust `ApplicationLifecycle` state. It may accept no Boolean, operation name, version, path, ID, nonce, authorization object, backup proof, integrity proof, database owner, or arbitrary frontend value. Only the first valid atomic consumption of `Pending` may succeed; repeated, concurrent, replayed, stale, or non-pending calls must create no authorization. A future coarse IPC result may distinguish only safe states such as `accepted`, `notPending`, and `unavailable`. `accepted` means only that Rust consumed `Pending` and retained the resulting authorization internally; the authorization must never be serialized or cross IPC.

The separately approved future cancellation direction is the migration-specific, argument-free `cancel_production_database_migration_confirmation`. It is non-authorizing, moves `Pending` to terminal `Revoked`, and makes later confirmation impossible in that process. Merely dismissing a future UI is insufficient if `Pending` would remain live; eventual abandonment must invoke this cancellation transition or an equivalent Rust-owned revocation. UI wording, modal behavior, styling, and workflow remain undecided.

No `ConfirmedMigrationIntent` abstraction is approved: it would duplicate the same trust fact without adding a separate boundary. The implemented private confirmation transition directly constructs and internally retains `ProductionDatabaseMigrationAuthorization`. The authorization is private, non-`Copy`, non-`Clone`, non-serializable, non-persistent, redacted, and exactly-once consumable.

A compromised renderer could invoke the future argument-free confirmation command while a legitimate Rust-owned `Pending` opportunity exists. In this locked first-generation design, invocation during that exact context represents operator consent, not authenticated identity. This boundary does not protect against a compromised renderer; stronger assurance would require separately approved application authentication, trusted UI, or another stronger confirmation mechanism. This residual risk neither permits frontend construction of privileged state nor weakens the requirement that only Rust can establish `Pending`.

The Rust state machine was implemented and tested before migration execution. Later repository work adds the Rust-owned production opportunity and revalidation path while keeping authority internal. The confirmation/cancellation Tauri commands and frontend flow remain unimplemented, and migration execution still cannot be inferred from `Pending` or authorization.

## 26. Implemented migration recovery-envelope cryptographic contract

The implemented `VerifiedEncryptedProductionDatabaseMigrationBackupStage` proves that an encrypted SQLCipher migration-backup stage was copied from the exact full-integrity-validated migration source using the same production database key; independently passed cipher and full SQLite integrity; exactly matched source metadata and headers; established ciphertext at rest; retained the source unchanged; and preserved source-bound migration authorization. The first and second digital recovery sets are each independently complete-set verified and composed into final keyless Layer D proof. Operational portable recovery remains absent because C2b remains unreachable and manually unvalidated, and Layer D lifecycle manifest publication and later composition remain unimplemented.

The implemented pure **Migration Recovery Envelope Format Version 1** uses the exact magic/domain `CHMRECV\0`, format version `1`, algorithm identifier `1`, exactly **XChaCha20-Poly1305**, a uniformly random 256-bit migration recovery key, a uniformly random 192-bit nonce per envelope, and the construction's untruncated fixed 128-bit authentication tag. The envelope is exactly 182 bytes; its payload is exactly 96 bytes and its AAD is exactly 44 bytes. Version 1 accepts only XChaCha20-Poly1305 and has no negotiation or fallback. Plain ChaCha20, 96-bit-nonce ChaCha20-Poly1305, AES-CBC, AES-CTR, unauthenticated encryption, HMAC-only protection, DPAPI as the portable envelope, and SQLCipher as an arbitrary payload cipher are prohibited.

The recovery key is generated separately from the repository-approved operating-system randomness source and represented by a dedicated migration-recovery-key type that is non-`Clone`, non-`Copy`, non-serializable, manually redacted for `Debug`, best-effort zeroized on drop, and plaintext only process-locally during envelope construction or verification. The implementation generates an independent nonzero 128-bit recovery-key-generation identifier and an independent nonzero opaque 128-bit migration-backup-set identifier. Neither is secret or key material. The backup-set identifier does not reuse the setup-publication identifier, installation identifier, database-key-generation identifier, or recovery/replacement generation.

Every envelope receives a fresh, independent uniformly random 192-bit XChaCha20 nonce from operating-system randomness. Reuse under the same recovery key is prohibited. There is no nonce counter, persisted global allocator, or deterministic derivation from any identifier, digest, timestamp, path, metadata, or key material. Randomness failure fails closed. The nonce is encoded in the envelope and is not secret; the intentionally large random nonce space avoids persistent nonce-allocation state.

The encrypted payload contains exactly: the 256-bit production database key, the 128-bit database-key-generation identifier, the 128-bit migration-backup-set identifier, and the 256-bit SHA-256 digest of the exact closed encrypted backup-stage database bytes. The digest is computed only after the backup writer has closed successfully and the stage has achieved `VerifiedEncryptedProductionDatabaseMigrationBackupStage`. It is not secret, but it is authenticated so the encrypted database artifact cannot be swapped independently of the envelope. Parish, installation, installation-generation, recovery/replacement-generation, setup-publication, `application_id`, `user_version`, schema-version, database-format-identity, evidence/freshness-key, active-DPAPI-wrapper, path, and timestamp data are excluded unless later architecture proves a need; database identities remain independently verified from the recovered SQLCipher database.

The exact 44-byte immutable envelope framing is associated authenticated data. It binds the permanent Church App migration-recovery-envelope domain separator, envelope format version, algorithm identifier, recovery-key-generation identifier, and externally framed backup-set identifier. Evidence-envelope and freshness-envelope domains are not reused.

Before any production database-key plaintext is released to a caller, framing, exact version, exact algorithm, structural identifier validity, and ciphertext length must be valid and AEAD authentication must succeed. Wrong recovery keys and authentication failures release no candidate key, and unauthenticated plaintext inspection is prohibited. After opening, the payload backup-set identifier must equal the authenticated envelope/set identifier, its database-key-generation identifier must correspond to recovered database metadata, and a fresh hash of the encrypted stage must equal the authenticated payload digest. Any mismatch fails closed.

The implemented consuming transition hashes the exact retained stage twice with SHA-256: once before sealing and once after authenticated opening/candidate recovery. For construction it independently reloads, recovers, and exactly binds the live protected database-key wrapper, then destroys that wrapper-derived `GenerationBoundDatabaseKey` after sealing and before independent envelope opening. Verification does not reload the live wrapper. It strictly parses, authenticates, and decrypts the envelope, reconstructs a fresh generation-bound database-key candidate using the existing trusted installation assessment, requires exact backup-set and authenticated digest equality, and reopens the same retained stage using only the envelope-recovered key. That open is `READ_ONLY`, `FULL_MUTEX`, `PRIVATE_CACHE`, `NOFOLLOW`, uses the fixed win32 VFS with no `CREATE`, performs canonical pre-key hardening, applies the key once, and enables/verifies `query_only`. Verification runs canonical cipher integrity and fixed metadata/header observation with exact source equality, explicitly closes the verifier, and finally revalidates stage identity before returning `VerifiedRecoveryEnvelopedProductionDatabaseMigrationBackup`. The retained stage carries its parent handle/identity, read-only leaf handle, and full leaf `FILE_ID_INFO`; the leaf excludes incompatible ordinary write/delete access.

A second full SQLite integrity scan is deliberately not required during envelope verification when the prior encrypted-stage proof passed full integrity, the authenticated SHA-256 digest proves byte identity with that stage, recovered-key cipher integrity succeeds, and exact metadata/header equality succeeds. If digest equality cannot be established, fail rather than substitute weaker verification. The database stage is never mutated merely to make it recoverable; recovery binding stays external to SQLCipher.

The portable envelope is not DPAPI-encrypted. CurrentUser DPAPI may later protect an optional local convenience copy of the recovery key, but such a copy is never sufficient portable-recovery custody. Envelope creation preserves recovery/replacement generation; only a separately authorized future recovery/replacement transition may increment it. The envelope grants no migration or startup authorization, database-write or restore authority, evidence/freshness authority, or mutation authority. On failure the implementation destroys migration authorization before returning outward, explicitly closes the source on primary failure, preserves canonical source-close retry ownership and verifier-close-only retry ownership, exposes only coarse errors with redacted `Debug`, retains stage/envelope artifacts without automatic destructive cleanup, and places no recovery-key material in outward failure owners.

The layers remain independent: (A) the implemented encrypted migration-backup stage; (B) the implemented cryptographic recovery envelope and private verification integration; (C1) the implemented custody codec/private ownership-state foundation; (C2a) the implemented private Windows native custody adapter; (C2b) the implemented lifecycle/main-thread/real-main-window dispatch, which remains normally unreachable and manually unvalidated; (D) independently complete-set-verified first and second digital recovery sets plus final keyless aggregate proof implemented, with lifecycle composition implemented through first-database publication and later composition still unimplemented; (E) unimplemented restore; and (F) unimplemented retention/deletion. The approved dependency for B remains unchanged. Cross-process migration exclusivity remains a separate thread-affine worker-local safety gate and is not owned by custody.

Version-1 recovery-envelope implementation tests reject a wrong recovery key; altered format/domain identity; unsupported version or algorithm; zero or invalid generation identifier; altered nonce, ciphertext, or tag; truncation or trailing bytes; altered authenticated backup-set association or digest binding; and association with a different encrypted backup database.

Verified custody is keyless and advances to `CustodyVerifiedAwaitingPublication`; the first Layer D lifecycle slice now dispatches the existing native picker for recovery device 1, retains the canonical eligible NTFS root, observes production topology through the retained source, and retains the root only after canonical physical-device separation succeeds.

For first-volume selection, `Cancelled` and `Unavailable` are retryable parked outcomes, not terminal migration outcomes. Both preserve the exact custody-verified source and worker-held migration exclusivity, keep `migration_work_resolved = false` and `CustodyVerifiedAwaitingPublication`, create no root authority, perform no cleanup or source close, and never redisplay automatically. A later explicit private worker command may start one new picker attempt from the same owner. Retained-root rejection, production-topology failure, and separation failure have the same parked-source policy and require a new native selection. Successful first-root preparation retains the custody source plus `RecoveryVolumeRootSeparatedFromProductionStorage`, advances only to the coarse first-root-retained-and-separated state, and starts no second picker, capacity check, child creation, publication, custody re-entry, or migration execution. Shutdown drops the first-root authority without recovery-device mutation and resolves the source through the existing custody abort/source-close/close-only-retry chain.

Shutdown and the main-thread take meet at one explicit ownership boundary. If shutdown intent wins before the main-thread take, Prepared remains unexposed and is recovered for terminal pre-exposure shutdown handling. If the main-thread take wins, shutdown cannot reconstruct or reclaim Prepared and waits for the ownership-bearing C2a outcome. Verified custody has an explicit terminal shutdown path through `abort_for_shutdown()`. Source-close failures retain only the appropriate close-only retry owner. Completion-send failure and impossible ownership states fail-stop instead of silently dropping authority. None of these paths can publish or execute migration.

The shutdown-race claim is exactly `NoWork`, `Ready(OperationalProductionDatabase)`, or `ShutdownWon(AuthorizedProductionDatabaseMigrationHandoff)`. Not authorized means no work. Authorized plus `Ready` follows normal preparation. If authorization exists but ordinary shutdown already removed the operational owner, the migration worker consumes the exact authorization once, skips full integrity, staging, envelope, and custody, and closes the exact authorized migration source. Failure remains worker-local and close-only retryable with exclusivity retained. The operational owner already extracted by ordinary shutdown remains solely in the ordinary shutdown close path, so neither owner is double-closed.

Operational reachability remains incomplete: there is no production invocation of migration discovery, migration confirmation Tauri command, cancellation command, or frontend migration UI. C2a, C2b, and first- and second-recovery-volume lifecycle selection are implemented but remain unreachable through normal product interaction. Custody and selection grant none of those authorities and do not grant restore authority; React remains non-authoritative.

## 29. Approved Layer D durable recovery publication architecture (partially implemented)

The implemented Layer D chain begins from the existing keyless `RecoveryKeyCustodyVerifiedProductionDatabaseMigrationBackup`; after independently publishing and completely verifying both recovery sets, its final aggregate transition consumes only `SecondCompleteRecoverySetVerified` and produces the keyless Rust-owned capability `TwoCompleteRecoverySetsVerifiedProductionDatabaseMigrationBackup`. That success proves only that two complete digital replicas of the same logical migration backup set were independently published and verified, with approved device-separation checks succeeding at verification time and the two-paper-copy custody layer already complete. It grants no migration execution, writable database ownership, schema mutation, restore, replacement, retention, deletion, or cleanup authority, and it does not prove later physical separation or continuing media availability.

Exactly two physically distinct, physically disconnectable external recovery devices are required. Each must be distinct from production storage and from the other recovery device and must contain one independently selected, validated, published, reopened, and verified digital recovery set. A partition, volume, directory, mount point, or drive letter on the same physical device is not a second device. The existing two verified paper copies remain required but separate: each paper copy is separate from both devices and from the other paper copy; either valid paper copy may recover either valid digital set; no permanent paper/device pairing or later physical-separation proof is recorded.

One complete digital recovery set uses exactly the fixed Layer D artifact names `parish-data.db`, `migration-recovery-envelope-v1.bin`, and `recovery-set-v1.manifest`. These names are constants, not operator input or manifest fields; no suffix, localization, alias, case variation, arbitrary filename, or path field is permitted. The first two artifacts are the exact encrypted SQLCipher migration-backup bytes and exact existing recovery-envelope bytes. The manifest is deterministic non-secret inventory and the publication commit marker, not a cryptographic trust root, authenticity proof, migration/restore/publication authority, or substitute for complete Layer D verification. Presence alone is insufficient. Completeness requires final publication followed by fresh reopening from the selected device and independent verification.

Recovery Set Manifest Format Version 1 is exactly 98 bytes. Bytes `0..8` are magic `CHLDRSM\0` (`43 48 4C 44 52 53 4D 00`); `8..10` are unsigned big-endian `u16` version 1 (`00 01`); `10..26` are the exact raw 16-byte migration backup-set identifier; `26..34` are the unsigned big-endian `u64` byte length of `parish-data.db`; `34..66` are the raw SHA-256 digest of the complete exact database bytes; and `66..98` are the raw SHA-256 digest of the complete exact 182-byte `migration-recovery-envelope-v1.bin`. There is no total-length field, trailing data, reserved byte, padding, flag, extension area, optional or variable-width field, delimiter, terminator, version negotiation, or fallback parser.

The strict parser accepts only exact length, magic, and version before copying or decoding exact-width fields into `ParsedUntrustedRecoverySetManifestV1`; its only semantic error categories are `WrongTotalLength`, `WrongMagic`, and `UnsupportedVersion`. Structural validation then rejects only an all-zero backup-set identifier (`InvalidBackupSetIdentifier`) or database length outside the inclusive range `512..=281_474_976_579_584` (`InvalidDatabaseByteLength`), in that order, and yields `RecoverySetManifestV1`. Every 32-byte digest is structurally representable. Only that validated type may canonically encode to the exact 98 bytes, and every accepted structurally valid manifest satisfies `encode(validate(parse(bytes))) == bytes` byte-for-byte. Parsing, validation, and encoding perform no hashing, digest comparison, filesystem or database operation, envelope parsing, allocation authorization, or authority construction. Production formatting exposes only coarse type/state and fixed error names, never complete identifiers or digests, manifest bytes, database length, attacker-controlled values, paths, or device/destination identity.

The manifest implicitly inventories Migration Recovery Envelope Format V1 under the fixed envelope name and exact 182-byte length without duplicating its name, version, or length. Any incompatible future envelope requires separately approved manifest-format evolution. The private dependency-free pure Rust codec is implemented: exact constants, strict parsing, separate structural validation, canonical `[u8; 98]` encoding, coarse redacted `Debug`, and focused deterministic tests. `RecoverySetManifestV1::from_trusted_internal_facts` is also implemented as a narrow crate-private constructor from the canonical identifier, `u64` database length, database digest, and envelope digest; it retains the locked inclusive length check `512..=281_474_976_579_584` and changes no format, parser, validation taxonomy, offset, encoding, or authority limit.

The retained custody-verified owner remains keyless and now provides the private borrowed `prepare_recovery_set_manifest_v1(&self)` boundary. It derives the canonical `MigrationBackupSetIdentifier` only through the retained independently verified envelope's strict parser/accessor path; observes initial stage metadata length; streams the retained read-only verified stage from byte zero with the existing 64 KiB bounded buffer, checked `u64` counting, and SHA-256; revalidates stage identity; observes final length; and requires initial length, final length, and streamed count to agree. The existing stage-digest path reuses this observation primitive. It freshly hashes the exact retained `[u8; 182]` envelope in memory, then invokes the trusted constructor. Success and each coarse redacted failure (`SourceObservationUnavailable`, `StageIdentityUnavailableOrChanged`, or `ManifestConstructionRejected`) preserve the original owner for later Layer D work or its existing shutdown path. The operation exposes no path, handle, connection, secret, publication capability, or migration authority.

Manifest construction alone does not create a recovery set. Retained-volume/device/root/capacity authority, fixed-child creation, and first-set publication remain separate prerequisites. The implemented consuming boundary combines the recovered-key predecessor with exact pre/post three-entry layout enumeration, fresh identity-bound reopening of all three artifacts, exact length/digest/EOF and backup-set correspondence, trusted-source reobservation, and destination/root/device continuity to create the keyless `FirstCompleteRecoverySetVerified` owner. Subsequent consuming transitions publish the second set's canonical `parish-data.db` from that owner's retained original verified migration source, publish `migration-recovery-envelope-v1.bin` from the retained original verified envelope, and publish `recovery-set-v1.manifest` last from freshly reconstructed original trusted source facts. Each transition independently revalidates relevant source, destination, device, and predecessor continuity and freshly verifies its artifact. The keyless `SecondCompleteRecoverySetVerified` consumes the published two-set predecessor plus one fresh owned custody record, proves the exact second-directory layout, freshly reopens and source-binds all three artifacts, authenticates the actual fresh envelope, verifies the fresh second database with the recovered key, explicitly closes the verifier, and repeats continuity/layout validation. The final owner consumes only that proof and revalidates current non-secret continuity without another custody or recovered-key verification. Private native exact-root selection and lifecycle composition through retained fixed-child directories are implemented. The strongest namespace/directory durability proof, lifecycle artifact publication and later integration, normal product reachability, restore, retention/deletion, and migration execution remain unimplemented.

The two sets are replicas of one logical backup set: identical encrypted-backup bytes, identical recovery-envelope bytes, and the same migration-backup-set identifier. Set 2 is published from the retained verified source, not copied from set 1. No second key, identifier, envelope, or encrypted backup generation is created. Destination selection and authority are Rust-owned through a future native Windows path. React may request only coarse workflow actions and must never supply or receive trusted paths, attest device identity or separation, construct publication authority, declare completeness, or receive secrets, handles, or device-authority values over IPC. Production topology validation must fail closed on ambiguity, unavailability, inconsistency, substitution, or unsupported storage; existing test-only candidate classifiers are not production authority.

Publication is create-new, no-replace, no-merge, no-overwrite, no automatic repair or deletion, and no partial-publication resume. A conflicting or incomplete destination fails closed; a retry starts with a newly selected suitable destination, while partial artifacts remain for separately authorized future handling. The first-database failure owner now has one private consuming abandonment boundary that drops represented destination and partial-artifact authority through ordinary Rust destruction, mutates no filesystem state, and returns only the original custody-verified source for fresh destination selection or its existing shutdown-close chain. A failed native writer `CloseHandle` is ownership-ambiguous and therefore fail-stops instead of returning that recoverable owner. Layer F owns future retention/deletion. The application-local encrypted source stage remains retained after zero, one, or two complete sets; Layer D has no deletion authority.

Final verification independently reopens each destination's fixed final layout and checks manifest/inventory correspondence, exact backup-set identifier, exact encrypted-backup and envelope correspondence with the retained verified source, envelope binding to the encrypted database, recovered-key verification against the reopened database, canonical metadata/header checks, canonical integrity appropriate to the existing recovery chain, and destination/device continuity and separation. Either valid paper bearer record may support any required paper entry; no paper identity or pairing is recorded.

The durability claim is bounded to successful supported writes, file-buffer flushes, closes, final-name publication, the strongest technically available supported namespace/directory durability operation, and fresh reopen/verification. It does not claim absolute survival of sudden power loss, defective media, controller/firmware failure, unsafe removal, or long-term degradation.

Failure, cancellation, and shutdown preserve fail-closed ownership. Conceptual progress distinguishes zero complete sets, first-set publication, one complete set, second-set publication/partial, and two complete verified sets. Shutdown prevents new Layer D work, destroys secrets and closes owned handles as required, retains close-only ownership where necessary, starts no cleanup/replacement/migration/new-destination work, and reports no Layer D success unless both sets were already fully established. Process-local capability state does not survive restart; disk artifacts require revalidation before any future adoption.

## 30. Recovery-volume lifecycle composition

The first Layer D lifecycle slice is implemented. From worker-held `RecoveryKeyCustodyVerifiedProductionDatabaseMigrationBackup`, the migration worker schedules the existing native picker on the main thread, resolves the real `main` window and `HWND`, and keeps the exact source plus migration exclusivity off `LifecycleInner`. A selected device is consumed only through the canonical eligible NTFS retained-root transition and canonical production/recovery physical-device separation using the production topology projected through the retained migration source. Success retains the exact source plus `RecoveryVolumeRootSeparatedFromProductionStorage`; `migration_work_resolved` remains false and exclusivity remains held.

For first-volume selection, `Cancelled` and `Unavailable` are retryable parked outcomes, not terminal migration outcomes. Both preserve the exact custody-verified source and exclusivity, keep `CustodyVerifiedAwaitingPublication`, create no root authority, close no source, perform no cleanup, and never redisplay automatically. A later explicit private worker request may make one new attempt. Retained-root rejection, production-topology failure, and separation failure follow the same parked-source policy and require a new selection. Shutdown before the main-thread take prevents the picker; shutdown after the take waits for the outcome and wins over adoption.

Second-volume selection is allowed only from the worker-held source-plus-first-root state and uses the same main-thread picker, real `main` window `HWND`, and canonical native selector. `Cancelled`, `Unavailable`, and second-root retention failure preserve the source, first root, exclusivity, first-root coarse state, and unresolved migration work for a later explicit internal retry. The selected second root is consumed first through canonical retained-root validation and then with the first root through canonical two-root separation. Any failure after entering that consuming transition loses both root authorities and returns to custody-only `CustodyVerifiedAwaitingPublication`; later work must freshly select device 1 and device 2. Success retains the exact source plus `TwoRecoveryVolumeRootsSeparatedFromProductionStorage` and immediately continues on the migration worker unless shutdown intent has already won.

Capacity composition borrows the exact custody-verified source to call its canonical `prepare_recovery_set_required_bytes()` observation, then consumes both roots only through `validate_recovery_volume_capacities_for_lifecycle`, the narrow facade over the canonical capacity transition. A pre-consumption required-byte observation failure preserves source plus both roots at `TwoRecoveryVolumesRetainedAndSeparatedAwaitingCapacity`. Any failure after the canonical transition consumes the roots retains only the source, returns to `CustodyVerifiedAwaitingPublication`, performs no device cleanup, and requires fresh selection of both devices; no automatic retry occurs. Capacity is a current observation only, not reservation, preallocation, durability proof, or guarantee that later writes fit.

Capacity success immediately continues on the migration worker through `create_recovery_set_directories_for_lifecycle`, the narrow facade over the canonical fixed-child transition. The lifecycle neither supplies nor derives the exact `church-app-recovery-set` name. Directory success retains the exact source plus canonical `TwoRetainedRecoverySetDirectories`; unless shutdown has already won, the same worker immediately consumes that exact owner through canonical `publish_first_recovery_database_artifact`. Database success is guarded once more by shutdown intent and then consumed on the same worker through the narrow canonical first-envelope publication facade. Envelope success parks exact `FirstRecoveryDatabaseAndEnvelopeArtifactsPublished` at `FirstRecoveryDatabaseAndEnvelopePublishedAwaitingManifest`; `migration_work_resolved` remains false and migration exclusivity remains held. Ordinary database or envelope publication failure immediately consumes its abandonment boundary, retains only the original custody source, returns to `CustodyVerifiedAwaitingPublication`, performs no cleanup or retry, and requires fresh destination selection beginning with device 1. Shutdown before envelope publication consumes the database-success abandonment; shutdown after envelope success consumes the database-plus-envelope success abandonment. Both leave published or partial database/envelope files untouched and then use the canonical source abort and close-only retry chain. Ambiguous native envelope-writer close remains terminal fail-stop. Manifest publication, custody re-entry, independent complete-set lifecycle composition, final aggregate lifecycle composition, normal product reachability, and migration execution remain unimplemented.
