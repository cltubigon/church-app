# Project overview

Fresh canonical Exact-V2 startup ends in one Rust-owned writable business database worker. The transition explicitly resolves the startup read-only connection first, reuses the canonical protected-key recovery and SQLCipher raw-key application boundaries, revalidates Exact V2, enables and reads back foreign-key enforcement, and moves the sole connection into a fixed-capacity serial worker with deterministic checked shutdown/close. Exact V1 never receives this authority: parish workflows remain unavailable, while one coarse Rust-owned capability and argument-free request make the existing protected migration discovery and native initial confirmation/cancellation ceremony reachable. The worker implements sealed request, occurrence, scheduling, completion, occupancy, and cancellation-review operations. Typed Exact-V2-only IPC projects frontend-safe DTOs through process-session opaque references, and React implements Requests, Scheduling, and Cancellation Review workflows. Restore and retention/deletion remain unimplemented.

Church App is intended to support a Roman Catholic parish through a Windows-first, desktop-first application that must operate offline. Future encrypted local parish data will be authoritative; central Supabase infrastructure is planned to be non-authoritative. The public Next.js surface and canonical contracts are intended for separate repositories and neither exists here.

This repository provides a Tauri 2 Windows desktop foundation plus the first Exact-V2 Requests, Scheduling, and Cancellation Review workflows. It remains pre-release and must not receive real parish data until the required manual Windows business-flow validation and release-readiness work are complete.

## Pre-exposure recovery-key custody retry

If the native recovery-key paper-copy ceremony is cancelled or unavailable before disclosure, Rust retains the exact prepared custody owner and reports a dedicated retryable migration state. The shell offers only `Resume recovery-key ceremony`; the argument-free request redispatches that same process-local owner through the canonical native ceremony. It does not regenerate the recovery key, backup, envelope, authorization, or migration source, and a process restart cannot reconstruct the authority. Cancellation or failure after disclosure remains terminal under the existing policy.

First-time setup presentation is separately gated by a Rust-owned capability produced only by the canonical never-initialized startup observation. Generic unavailability and installed migration-preparation states do not expose setup.

## Resolved migration-preparation failure

Real Windows migration testing exposed that a fail-closed preparation error could resolve its privileged ownership and then close the whole application without a user shutdown request. Resolved migration work now permits process exit only when the existing Rust-owned shutdown intent is also present; `may_exit()` remains a safety check, not an instruction to exit. Without shutdown intent, Church App stays open in the coarse unavailable state, with first-time setup and immediate migration retry unavailable. The observed existing fixed-stage conflict still fails closed, and no stage cleanup, overwrite, adoption, resume, or repair behavior was added. The complete migration ceremony still requires manual Windows validation.

The first business-schema product behavior and physical design remain exactly `ServiceRequest`, `RequestScheduleOccurrence`, and `RequestCancellationReview`, mapped to `service_requests`, `request_schedule_occurrences`, and `request_cancellation_reviews`. The fixed persisted service codes are `baptism`, `confirmation`, `wedding_marriage`, `burial_funeral`, and `first_communion`; no configurable catalog exists. Requests and cancellation reviews are created by Rust with `pending`, with no SQLite lifecycle default. Scheduling uses separate minute-precision `Asia/Manila` occurrences, and only `scheduled` requests occupy an exact local date/time slot. Requester data remains a bounded request-local contact snapshot; normalized people/parishioners and permanent or sacramental records remain deferred. The approved business mutation service, typed IPC, and first-release workflow forms are implemented without broadening this exact three-table contract.

The implemented database capability includes encrypted local schema-version-1 bootstrap, the gated transactional 1 -> 2 migration, and ordinary read-only startup adoption of an exact schema-version-2 database after the required process restart. Both supported schema versions retain metadata contract version 1, `application_id = 0x43484150`, and the existing `ApplicationDatabaseFormatIdentity`. The only defined compatibility direction is 1 -> 2; newer versions remain unsupported and downgrade-refused, inconsistent states fail closed, and no generic unsupported-to-2 rule exists. Exact V2 startup observation grants no migration, repair, downgrade, or business authority by itself; business commands become available only after the lifecycle reaches Ready with the bounded Exact-V2 worker. The application still excludes authentication, Supabase integration, public intake, synchronization, restore, replacement, retention/deletion, PDFs and printing, updates, telemetry, reports, certificates, and broader parish record workflows. The first release direction is English only, but localization behavior is not implemented.

## Reachable post-recovery migration confirmation

The shell now shows one migration-authorization action only after Rust reports `TwoCompleteRecoverySetsVerifiedAwaitingMigrationExecution`. It invokes one argument-free command; React cannot send the confirmation decision or any trusted value. A Rust-owned Win32 modal, parented to the real application window and dispatched on the main thread, produces `Confirmed`, `Cancelled`, or `Unavailable`.

Fresh confirmation consumes the exact final Layer D owner into a single-use process-local owner and reports only `MigrationExecutionConfirmedAwaitingWritablePreparation`. Cancellation and unavailability remain retryable at the prior state. Shutdown arbitration preserves the existing source-only abandonment and close-retry chain.

## Writable V1 migration preparation

After fresh confirmation, Rust now revalidates the retained final recovery/source proof, recovers a bounded generation-bound key through the existing custody path, closes the retained read-only source connection, and prepares the canonical application-owned `parish-data.db` with a migration-specific writable SQLCipher connection. Hardened file identity, key application, integrity, metadata/header, exact V1 physical schema, `user_version = 1`, and restart classification are checked before success. The key owner is dropped after application.

Prepared ownership now continues on the migration worker through one fixed `BEGIN IMMEDIATE` transaction. The transaction executes the canonical eight V2 DDL statements, guardedly changes only the singleton metadata schema version from 1 to 2, sets `user_version = 2`, and commits once. Pre-commit failures roll back; any commit error is treated as ambiguous and is never retried.

After a successful commit, the same writable connection is freshly checked for retained identity, cipher integrity, SQLite quick-check, exact unchanged metadata identities, exact V2 schema, empty business tables, and `ExactV2` restart classification, then explicitly closed. Success reports only `MigrationCommittedRestartRequired`; operational V2 remains unavailable in that process. On a fresh process, ordinary keyed read-only startup observes and canonically classifies the current disk state before evidence correspondence and freshness. Exact V2 continues through the unchanged correspondence, freshness, final-installation, startup-authorization, activation, and checked-close chain to ordinary `Ready`; exact V1 preserves its existing behavior. Inconsistent and unsupported-newer states fail closed, and V2 never re-enters migration discovery. Recovery artifacts and the local migration backup are retained. Restore, replacement, retention/deletion, broader parish workflows, and manual business-flow validation remain unimplemented.
