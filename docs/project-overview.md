# Project overview

Church App is intended to support a Roman Catholic parish through a Windows-first, desktop-first application that must operate offline. Future encrypted local parish data will be authoritative; central Supabase infrastructure is planned to be non-authoritative. The public Next.js surface and canonical contracts are intended for separate repositories and neither exists here.

This repository currently provides only a Tauri 2 foundation: an accessible React shell, four unavailable placeholder areas, a typed Rust health command, focused tests, and narrow validation. It is not a usable parish application and must not receive real parish data.

The first business-schema product behavior and physical design are approved only as documentation and remain exactly `ServiceRequest`, `RequestScheduleOccurrence`, and `RequestCancellationReview`, mapped to `service_requests`, `request_schedule_occurrences`, and `request_cancellation_reviews`. The fixed persisted service codes are `baptism`, `confirmation`, `wedding_marriage`, `burial_funeral`, and `first_communion`; no configurable catalog exists. Requests and cancellation reviews are explicitly created by future Rust code with `pending`, with no SQLite lifecycle default. Scheduling uses separate minute-precision `Asia/Manila` occurrences, and only `scheduled` requests occupy an exact local date/time slot. Requester data remains a bounded request-local contact snapshot; normalized people/parishioners and permanent or sacramental records remain deferred. No business table, executable DDL, schema version, V2 designation, migration, form, IPC, workflow, record, schedule, or business domain code is implemented here.

The implemented database capability remains limited to encrypted local bootstrap metadata and its Rust-owned trust and lifecycle foundation. The application still excludes an implemented parish/business schema, migration, authentication, Supabase integration, public intake, synchronization, backup and recovery, PDFs and printing, updates, telemetry, reports, certificates, and all real workflows. The approved physical design would require a future schema-version change and forward migration for schema-version 1 installations, but its target version remains unapproved. The first release direction is English only, but localization behavior is not implemented.
