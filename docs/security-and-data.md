# Security and data

- Never place secrets, tokens, credentials, or production environment configuration in the frontend or repository.
- Never place sensitive parish or personal data in logs, tests, examples, or screenshots. Tests use synthetic bootstrap strings only.
- Privileged operations belong in Rust. React must not directly access files, a future database, encryption material, or privileged services.
- Production database paths cannot be supplied by frontend values, command arguments, environment variables, command-line values, or user-selected strings. No Tauri command returns the production directory, database filename, database path, Windows username, or filesystem metadata.
- Production setup authorization is an in-memory Rust type with a private field, created only by a dedicated transition from never-initialized evidence. Raw booleans, React or IPC values, CLI arguments, environment variables, paths, and arbitrary strings cannot construct it. No setup Tauri command exists.
- Ordinary startup has no setup authorization. Initialized-but-missing storage, inconsistent installation evidence, and unavailable evidence fail closed and cannot fall back to first-time setup or authorize creation.
- A structurally valid logical installation-evidence contract is still untrusted. It must not be treated as authenticated, authoritative, safe for startup, or matched to a database until separately approved authenticated-integrity and database cross-check boundaries exist.
- Its 164-byte canonical plaintext encoding is likewise untrusted, unauthenticated, and unprotected. The encoder contains no secrets beyond the modeled opaque identifiers, and neither complete encoded bytes nor opaque identifier values may be logged or exposed through debug output.
- The 226-byte authenticated-envelope parser validates framing only. Its terminal 32-byte tag field remains untrusted until HMAC verification succeeds; correctly framed bytes alone confer no integrity, provenance, database correspondence, startup permission, or operational authority.
- HMAC-SHA-256 verification uses the HMAC crate's `verify_slice` method over exact envelope bytes `0..194`. No ordinary tag equality or custom constant-time comparison is used. Authentication failures are coarse and redacted.
- The per-parish evidence-authentication key is represented only by a Rust-owned 32-byte private buffer independent from the database key. Production generation requests its bytes from the operating-system randomness provider and independently requests a nonzero 16-byte key-generation identifier. Key and generated identifier bytes do not enter React, IPC, serialization, logs, or ordinary `Debug`; no universal or deterministic key exists.
- Authentication-material generation fails closed on any randomness error and after three all-zero identifier fill attempts. It has no deterministic fallback and derives no entropy from application identifiers, parish or installation identifiers, HMAC output, environment, clock, process, thread, machine, user, path, filesystem, registry, or database values. Provider details, operating-system errors, generated bytes, hashes, fingerprints, and retry values are not exposed.
- Drop applies best-effort zeroization to the type's owned buffer, including partial failure after key ownership has been established. This does not erase compiler temporaries or pre-move stack remnants, prior caller copies, register or stack spills, future cryptographic-state copies, swap, hibernation, crash dumps, debugger snapshots, or microarchitectural leakage.
- Complete envelope bytes, inner plaintext bytes, authentication-key generation identifiers, and terminal tag bytes remain redacted from debug and error output. Malformed or unsupported total length, magic, version, algorithm identifier, key-generation identifier, or declared plaintext length fails closed without scanning, fallback, prefix acceptance, or trailing-byte acceptance.
- Authenticated results retain neither the authentication key nor its bytes. No key bytes, plaintext bytes, envelope bytes, tags, or generation identifiers enter logs, Tauri IPC, or frontend state.
- HMAC authentication does not provide freshness or prevent replay or rollback. Current key-generation policy, persistence, database correspondence, and operational authority remain separate future boundaries.
- Windows protection uses classic DPAPI current-user scope only. Local-machine scope cannot be selected, UI is forbidden, and callers cannot supply optional entropy, descriptions, prompts, reserved data, or generic flags. The opaque DPAPI result is never parsed or normalized.
- Native DPAPI failures collapse to coarse redacted operation errors; Windows codes and native text are not retained in ordinary errors. Successful unprotected native allocations are copied into short-lived Rust-owned containers, best-effort cleared with `zeroize`, and then released once with `LocalFree`.
- Clearing reduces residual plaintext but cannot guarantee erasure of compiler temporaries, register or stack spills, swap, hibernation, crash dumps, debugger snapshots, prior copies, or microarchitectural state. Current-user DPAPI is not a strong boundary against malware already executing as the same user or against administrators.
- DPAPI unprotection establishes only candidate bytes. It does not replace HMAC authentication, generation matching, structural validation, freshness, rollback protection, database correspondence, setup or startup permission, or operational authority. No protected object is persisted in this stage.
- Deterministic malformed-wrapper, protected-key payload, fake-protector, and corrupted real DPAPI inputs fail closed through either native rejection or a later strict application-validation boundary. Candidate key-payload parsing alone grants no HMAC, generation, plaintext, startup, or operational authority.
- This hardening reduces confidence risk around malformed and corrupted protected inputs but does not prove DPAPI or cryptographic security. Replay, rollback, same-user malware, administrator access, persistence, and database correspondence remain unresolved.
- Deterministic authenticated-envelope mutation tests show that the tested arbitrary byte mutations cannot create an authenticated result without a valid recomputed tag. A valid tag still establishes neither logical validity, freshness, current key-generation policy, database correspondence, startup permission, nor operational authority.
- Wrong-key, malformed-length, representative-pattern, full-position, boundary, and retagged-malformed-plaintext corpora retain coarse redacted framing and authentication errors. These tests reduce confidence risk around the implemented boundaries but do not prove cryptographic security.
- Strict parsing fails closed on malformed length, framing, encoding version, declared payload length, application-identifier length, or application-identifier UTF-8. There is no fallback parser, format guessing, trailing-data acceptance, or automatic normalization.
- Successfully parsed values remain untrusted until a separate structural-validation call succeeds, and structural success still does not establish authentication, persistence, provenance, database correspondence, startup permission, or operational authority. Parser errors and parsed-value debug output expose neither encoded content nor complete opaque identifiers.
- Deterministic parser mutation tests reduce confidence risk around malformed inputs, field overlap, canonicality, and panics, but do not prove security. No arbitrary input can create operational authority, and observed parse errors and parsed-value debug output remain redacted.
- The logical contract contains no secrets, paths, personal or sacramental data, passwords, recovery codes, key material, machine identity, Windows user identity, or protection metadata. Full parish, installation, database-key generation, and setup publication identifiers must not appear in logs or debug output; the contract's debug representation redacts them.
- The fixed production path is modeled beneath the application-owned per-user local application-data directory for `io.github.cltubigon.churchapp`. This stage performs no directory or database creation, opening, migration, or connection.
- Pure persistence paths are joined only beneath caller-supplied synthetic roots. New path wrappers and their aggregate have redacted `Debug` output; the presence facts contain no paths, timestamps, contents, or native errors.
- The protected-wrapper reader rejects empty, below-15-byte, and above-65,550-byte reported lengths before exact-size allocation. It retries interrupted reads, collapses premature EOF and other I/O failures to coarse categories, and rejects any byte observed by its single-byte trailing probe. It retains no native error and exposes no path, contents, or observed length through errors or debug output.
- Unavailable inspection has highest classifier precedence, unexpected entry types fail closed as inconsistent, and any observed stage file is non-authoritative unexpected staging. Conclusive clean absence is only `CleanAbsenceCandidate`; it grants no setup, creation, startup, database, or operational authority.
- The pure publication model describes required evidence-last ordering only. It performs no filesystem inspection or mutation and therefore makes no claim about ACLs, reparse points, volumes, atomic replacement, durability, races, flushing, or any other real filesystem security property.
- The Windows filesystem proof uses deterministic synthetic wrapper bytes only and runs only beneath unique test-owned temporary roots. Stage creation is `CREATE_NEW` with zero sharing; reloads use `GENERIC_READ` with `FILE_SHARE_READ`; initial publication uses only `MOVEFILE_WRITE_THROUGH`. Coarse errors and their `Debug` forms retain no path, native code or text, wrapper bytes, user/SID, volume, or identifier data.
- Existing-file replacement is also executable only in Windows tests. Its native call always supplies a null backup path, flags exactly zero, and null reserved pointers. A failed call captures only a private coarse failure family; raw native codes and text are neither retained nor exposed. No retry, rollback, restoration, or per-file cleanup follows the call; only exact test-root teardown is allowed after assertions.
- Fresh exact-name inspection, rather than the native return or failure family, is authoritative for the observed post-call state. Byte equality and canonical-wrapper validity do not prove ACL, security-descriptor, named-stream, timestamp, or other metadata equality. The success proof additionally requires stage-to-result file-ID continuity and old-active/result identity distinction.
- Stage and active handles are independently reopened and checked as disk files that are neither directories nor reparse points. Handle-reported sizes must remain in 15–65,550 bytes and unchanged across the existing bounded read. Normalized GUID final paths must match the validated test evidence directory and exact fixed filename, and UNC forms are refused. These checks reduce risk but do not prove complete reparse, junction, or TOCTOU resistance.
- The normal-tree hardening tests reject every reparse attribute and every nonzero known or unknown reparse tag, including inconsistent attribute/tag combinations. They use both full `FILE_ID_INFO` object identity and normalized namespace identity, retain directory handles across leaf validation, and require parent/leaf volume-serial and volume-GUID agreement.
- Exactly one link is required only for protected active and staged installation-evidence wrapper leaves. Zero or multiple links fail closed; directories and the future database receive no hard-link policy in this stage.
- A real Windows test fixture now confirms that both authentication-key wrapper names move from one link to two after `std::fs::hard_link`, that the alias shares the full `FILE_ID_INFO` identity and canonical bytes but not the normalized final path or approved exact name, and that hardening returns `HardLinkRejected` before reading or injected mutation. Alias-only removal restores the original identity, bytes, and one-link state. This grants no production filesystem or publication authority.
- A separate Windows-test-only fixture confirms that an exact normalized `installation-evidence` path and a byte-identical canonical wrapper do not establish directory continuity. A retained read-access target handle without delete sharing blocks the ordinary rename attempt; after target and descendant handles close, the original and prebuilt candidate can exchange namespace occupancy through two controlled `std::fs::rename` calls, and full `FILE_ID_INFO` discontinuity rejects the substitute before any continuation.
- That controlled substitution test stores no production identity and adds no production enforcement, repair, rollback, or winner selection. It does not mix reparse or hard-link objects into the case and makes no production safety claim; intermediate/root substitution, hostile concurrency, production local-volume enforcement and authority, broader host provenance, and removable/network policy remain deferred. The private Windows-test-only non-authoritative local-volume candidate classifier and controlled observations are already implemented.
- A separate Windows-test-only compatibility case retains the exact validated evidence-directory handle with read access and read/write sharing but no delete sharing while the accepted child replacement runs. The same handle's full identity, normalized path, disk-directory/reparse facts, and saved-parent volume relationship remain stable before the call, immediately after it, and after fresh child inspection. Retaining the parent reduces ordinary same-operation directory-substitution risk, but replacement remains path-based and not handle-relative; child-entry and cross-process races remain. No production identity persistence, enforcement, retry, repair, or rollback is added.
- The private Windows-test-only local-volume classifier trusts neither path spelling nor a drive letter as acceptance evidence. It starts from a retained validated handle, accepts only a strict normalized volume-GUID path, derives only that exact GUID root, and maps one `GetDriveTypeW` result into coarse facts. Actual paths, drive letters, GUIDs, device names, user information, and native errors are not exposed.
- The nested Windows-test-only device-property proof starts only after `LocalFixedCandidate`, retains the test-root handle, opens only its exact derived volume device with access zero and read/write sharing, and makes exactly two bounded `IOCTL_STORAGE_QUERY_PROPERTY` calls. It parses raw fixed fields, caps allocation at 65,536 bytes, never follows descriptor offsets, and exposes no path, GUID, device name, bus number, vendor, product, revision, serial, raw structure, native code, or native text.
- `DevicePropertyCandidate` means only that the approved volume open and bounded query succeeded, the exact installed layout version and stable size passed strict parsing, removable media was not reported, and the bus belonged to the approved candidate family. These driver-reported facts remain insufficient for device non-removability, hot-plug or surprise-removal assurance, internal placement, physical locality, USB-enclosure exclusion, VHD/VHDX or profile-container exclusion, remote-backing exclusion, durability, or production suitability. No hot-plug, physical-drive, disk-extent, device-interface, production-path, setup, startup, persistence, publication, replacement, database, DPAPI, IPC, or frontend authority is added.
- Wrapper identity, size, attributes, reparse tag, link count, and final path are re-queried on the same handle after the bounded canonical read, and retained directory identities are re-queried before and after it. Hardening errors and debug output contain no path or UTF-16 content, file ID, volume GUID or serial, native code or text, or wrapper bytes.
- This remains synthetic-tree test evidence only. The hard-link and single controlled exact-target substitution cases do not establish production path safety, general race resistance, hostile reparse or broader substitution handling, enterprise-profile support, local fixed-volume policy, removable-device or hot-plug safety, or production publication authority.
- Reload verification proves bytes visible through a new handle after `FlushFileBuffers`; it does not prove survival of sudden power loss. Test teardown removes only the unique test root and is not automatic production cleanup. No DPAPI, database, production resolver, setup/startup authority, IPC, or frontend capability participates.
- Ordinary Church App use may run under the current Windows account, and the process should run in a non-elevated session. Administrator-group membership need not be established for the accepted current-account evidence. A dedicated standard Windows account is optional and recommended for a parish-owned shared workstation; it is not an ordinary-use prerequisite. Elevation refusal is not yet implemented, and this direction does not approve privileged or elevated ordinary operation. Future local parish storage must be encrypted and authoritative. Carlo has selected SQLCipher Community Edition, and the exact Windows production dependency plus private raw-key primitive are implemented and accepted; the complete operational database-opening system remains deferred.
- Future central privileged credentials must remain server-side. Supabase is not configured here.
- Current logs are local development terminal output, limited to event name, outcome, and safe code. They contain no payload, raw error, environment value, machine identifier, path, user information, or parish data, and nothing is uploaded.

Automated checks do not prove security, accessibility, desktop runtime behavior, production storage safety, power-loss durability, or complete user flows. The Windows current-user, in-memory DPAPI protection/unprotection foundation, strict wrappers and recovery orchestration, and test evidence are already implemented; production persistence and loading of DPAPI-protected objects, active-generation policy, database correspondence, setup/startup integration, recovery, and operational policy remain deferred. The private Windows-test-only non-authoritative local-volume candidate classifier and controlled observations are already implemented; production local-volume enforcement and authority, broader host provenance, and removable/network policy remain deferred. The private Windows-test-only bounded device-property candidate inspection is already implemented; production device inspection and enforcement, hot-plug and surprise-removal assurance, physical/provenance policy, and operational authority remain deferred. Production replacement, rollback protection, production cleanup, ACL and replacement-metadata enforcement, named streams, backup, cross-volume behavior, mutex coordination, complete reparse/junction defenses, controlled virtual/profile/mounted-folder hosts, runtime replacement detection, and database creation also remain deferred.

## Approved production database security policy and narrow implemented gate

Carlo explicitly approved this bounded security architecture. The Windows production SQLCipher dependency and private raw-key application primitive are now current accepted capability. There is still no operational production database selection or connection-opening flow, key application in startup or setup, SQLite metadata read, SQLCipher integrity check, startup authorization, first-time creation, schema, migration, backup/restore, recovery, replacement, or frontend/Tauri database operation.

- SQLCipher Community Edition is mandatory for production parish databases, production backups, and production recovery databases. Plain SQLite and encrypted/unencrypted fallback are prohibited. Windows production now uses exactly pinned `rusqlite` 0.39.0 with default features disabled and only `bundled-sqlcipher-vendored-openssl`, under the Windows production dependency table. There is no Windows `rusqlite` development dependency and no direct `libsqlite3-sys` dependency. The former test-only dependency state and feasibility proof are historical evidence. Pinned SQLCipher/OpenSSL versions and the lockfile remain release evidence.
- The private Windows-only key-application boundary accepts only `&GenerationBoundDatabaseKey` and a caller-supplied already-open handle. It creates one fixed 67-byte owner containing exact lowercase `x'<64 hex characters>'`, invokes `sqlite3_key` exactly once, treats only `SQLITE_OK` as success, and best-effort zeroizes the owned encoded buffer. The key remains Rust/backend-only: it is not logged, serialized, sent through IPC, exposed to React, or accepted from a Tauri command.
- Native key-application failure exposes only `DatabaseKeyApplicationError::Failed`; no native status, raw error chain, key material, encoded key specification, handle value, path, SQL, or PRAGMA text is logged or returned. Primitive success proves only that SQLCipher accepted the one key-submission call. It does not prove handle provenance, key correctness, encryption, readability, integrity, metadata, correspondence, freshness, startup permission, or operational authority.
- The primitive has no active runtime caller and performs no connection open or close, database creation or selection, query, inspection, mutation, rekey, metadata read, integrity check, filesystem operation, logging, frontend work, Tauri command, or IPC operation.
- The independent database key is 256 random bits from the Windows OS cryptographic RNG. It is never password-derived, value-derived, or shared with the evidence HMAC key. Its owner is non-`Copy`, has no unrestricted `Clone`, redacts formatting, and best-effort zeroizes owned buffers.
- A dedicated CurrentUser-DPAPI wrapper protects the live database key. Portable recovery uses a separate random recovery key and an authenticated recovery envelope. Recovery-key custody, duplication, rotation, loss, and destruction are explicit operator/security duties; live-key DPAPI protection does not replace portable recovery policy.
- Metadata fails closed on a missing, duplicate, partial, wrong-class, wrong-length, unsupported, or malformed singleton row. In particular, `permanent_application_identifier` is bounded canonical UTF-8 SQLite `TEXT`, while `database_format_identity` is the existing typed `ApplicationDatabaseFormatIdentity` encoded only as an exactly 16-byte SQLite `BLOB`, directly decoded to that type and compared by exact typed equality. It is never text or a textual, numeric, hashed, prefixed, or fingerprint representation.
- Exact typed correspondence covers the permanent application identifier, database-format identity, parish identifier, installation identifier, database-key generation identifier, and setup-publication identifier. Generation values use lineage comparison. Evidence format fields stay evidence-only, and timestamps are diagnostic only.
- A separate CurrentUser-DPAPI-protected freshness anchor records the installation identifier, installation generation, recovery/replacement generation, database-key generation identifier, and setup-publication identifier. Database, evidence, and anchor must eventually agree. Stale evidence, stale database, opposing movement, and ambiguity fail closed.
- Freshness is rollback evidence, not cryptographic monotonic rollback prevention. Coordinated rollback of every local artifact and applicable profile state to a mutually consistent snapshot cannot be detected. HMAC, DPAPI, timestamps, and integrity checks do not remove that limitation.
- The approved production path is the exact application-owned directory and `parish-data.db` on local NTFS. Reparse points, symlinks, junctions, mount traversal, cloud placeholders, hard links, network or removable storage, unstable identity, unexpected sidecars, WAL, and SHM fail closed. Startup never deletes or repairs sidecars. A dedicated database adapter with database-aware race protection is required; evidence-wrapper loading is not a drop-in database hardening implementation.
- Ordinary inspection is read-only, no-create, bounded, one-attempt, query-only/defensive, and one consistent snapshot. It has no retry loop, writable fallback, `immutable=1`, migration, repair, journal recovery, key regeneration, or artifact creation. Extension loading is disabled, `trusted_schema` is off, and the busy timeout is at most five seconds.
- Every future open requires cipher-integrity and limited SQLite quick checking. Full integrity is required at controlled mutation and recovery boundaries. Cancelled or incomplete checks fail. There is no automatic repair, header/metadata repair, schema downgrade, journal-mode switch, VACUUM, or cleanup.
- Initial durability is rollback-journal `DELETE`, `synchronous=FULL`, explicit transactions, `secure_delete=ON`, and `auto_vacuum=NONE`; WAL/SHM and WAL checkpoints are outside the initial policy.
- Setup is the sole creation authority. Persisted presence, evidence validation, path validation, key recovery, opening, metadata decoding, integrity, correspondence, freshness, installation classification, startup authorization, and operational opening remain separate typed stages. Recovery, restore, migration, rekey, anchor replacement, database replacement, and destructive cleanup each require separate authorization. No generic repair authority exists.

The implemented primitive exposes only its coarse key-application failure. Future operational errors remain limited to database path invalid, database absent/open failed, key unavailable/application failed, wrong key or unreadable encrypted database, corrupt or unsupported database, unsupported metadata version, missing/duplicate/malformed metadata, evidence/database mismatch, stale evidence/database, rollback suspected, integrity-check failure, sidecar inconsistency, and unavailable inspection. Errors and logs expose no path, SQL or PRAGMA text, key, identifier, generation, metadata value, DPAPI data, native status code, raw error chain, username, or profile directory.

## Controlled-host harness safety boundary

The Windows-test-only harness records no path, drive letter, volume GUID, device number, vendor/model/serial, username, SID, native code/text, environment-variable contents, or raw descriptor bytes. It never enumerates drives or sibling entries, formats or repartitions media, changes labels, reads unrelated content, retries with elevation, or converts a result into authority.

For the USB case it mutates only one exact `church-app-usb-flash-proof-{pid}-{nanos}-{counter}` child beneath the manually supplied root and creates only `unrelated-sentinel.synthetic` inside that child. The sentinel must remain unchanged. Cleanup is attempted once against that exact child only; cleanup failure remains a failure. All production-policy, persistence, database-opening, setup, startup, publication/replacement, and installation-state authority fields remain false.

The controlled-host prerequisite diagnostic exposes only fixed stage names, `Unavailable` or `Rejected`, fixed sentinel states (`NotReached`, `Preserved`, `Unavailable`, or `Changed`), Booleans, and bounded call counts. It exposes no path, drive letter, GUID or serial, filesystem name, file identity, link count, native detail, device detail, user identity, environment value, raw UTF-16, or sentinel bytes. Child creation and sentinel-write failures remain possible generally but cannot explain the recorded USB failure because fixture construction completed and exact-root cleanup later succeeded. No filesystem-format cause is claimed.

On the accepted diagnostic USB rerun, unavailable `FILE_ATTRIBUTE_TAG_INFO` facts caused `DirectoryAttributeInfoUnavailable` with disposition `Unavailable` and prevented local-volume and device-property classification. Drive-type, volume-open, property-IOCTL, and hot-plug counts remained zero; sentinel verification was not reached. Exact-root cleanup was attempted once and succeeded, and the manual leftover-folder check found no entries. No path, drive letter, filesystem name, GUID, device identity, native error, or other sensitive host fact was retained, and every production and operational authority field remained false.
