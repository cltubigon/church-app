# Security and data

- Never place secrets, tokens, credentials, or production environment configuration in the frontend or repository.
- Never place sensitive parish or personal data in logs, tests, examples, or screenshots. Tests use synthetic bootstrap strings only.
- Privileged operations belong in Rust. React must not directly access files, a future database, encryption material, or privileged services.
- Production database paths cannot be supplied by frontend values, command arguments, environment variables, command-line values, or user-selected strings. No Tauri command returns the production directory, database filename, database path, Windows username, or filesystem metadata.
- Production setup authorization is an in-memory Rust type with a private field, created only by a dedicated transition from never-initialized evidence. Raw booleans, React or IPC values, CLI arguments, environment variables, paths, and arbitrary strings cannot construct it. The narrow argument-free setup Tauri command requests the Rust-owned transition but cannot construct or supply its authority.
- Ordinary startup has no setup authorization. Initialized-but-missing storage, inconsistent installation evidence, and unavailable evidence fail closed and cannot fall back to first-time setup or authorize creation.
- A structurally valid logical installation-evidence contract remains untrusted. Structural validation alone grants no database correspondence, startup authority, or operational authority; the implemented authentication, trusted-loading, database/evidence-correspondence, freshness, startup-authorization, and operational-activation boundaries must each be successfully traversed before their respective later trust or authority can exist.
- Its 164-byte canonical plaintext encoding is likewise untrusted, unauthenticated, and unprotected. The encoder contains no secrets beyond the modeled opaque identifiers, and neither complete encoded bytes nor opaque identifier values may be logged or exposed through debug output.
- The 226-byte authenticated-envelope parser validates framing only. Its terminal 32-byte tag field remains untrusted until HMAC verification succeeds; correctly framed bytes alone confer no integrity, provenance, database correspondence, startup permission, or operational authority.
- HMAC-SHA-256 verification uses the HMAC crate's `verify_slice` method over exact envelope bytes `0..194`. No ordinary tag equality or custom constant-time comparison is used. Authentication failures are coarse and redacted.
- The per-parish evidence-authentication key is represented only by a Rust-owned 32-byte private buffer independent from the database key. Production generation requests its bytes from the operating-system randomness provider and independently requests a nonzero 16-byte key-generation identifier. Key and generated identifier bytes do not enter React, IPC, serialization, logs, or ordinary `Debug`; no universal or deterministic key exists.
- Authentication-material generation fails closed on any randomness error and after three all-zero identifier fill attempts. It has no deterministic fallback and derives no entropy from application identifiers, parish or installation identifiers, HMAC output, environment, clock, process, thread, machine, user, path, filesystem, registry, or database values. Provider details, operating-system errors, generated bytes, hashes, fingerprints, and retry values are not exposed.
- Drop applies best-effort zeroization to the type's owned buffer, including partial failure after key ownership has been established. This does not erase compiler temporaries or pre-move stack remnants, prior caller copies, register or stack spills, future cryptographic-state copies, swap, hibernation, crash dumps, debugger snapshots, or microarchitectural leakage.
- Complete envelope bytes, inner plaintext bytes, authentication-key generation identifiers, and terminal tag bytes remain redacted from debug and error output. Malformed or unsupported total length, magic, version, algorithm identifier, key-generation identifier, or declared plaintext length fails closed without scanning, fallback, prefix acceptance, or trailing-byte acceptance.
- Authenticated results retain neither the authentication key nor its bytes. No key bytes, plaintext bytes, envelope bytes, tags, or generation identifiers enter logs, Tauri IPC, or frontend state.
- HMAC authentication does not provide freshness or prevent replay or rollback. Trusted evidence loading, database/evidence correspondence, freshness, startup authorization, and operational activation are distinct implemented boundaries composed by the Rust-owned lifecycle; none substitutes for another, and successful HMAC authentication alone grants none of the later authorities. Evidence persistence and publication policy, monotonic rollback protection, and broader operational database authority remain separate and unimplemented.
- Windows protection uses classic DPAPI current-user scope only. Local-machine scope cannot be selected, UI is forbidden, and callers cannot supply optional entropy, descriptions, prompts, reserved data, or generic flags. The opaque DPAPI result is never parsed or normalized.
- Native DPAPI failures collapse to coarse redacted operation errors; Windows codes and native text are not retained in ordinary errors. Successful unprotected native allocations are copied into short-lived Rust-owned containers, best-effort cleared with `zeroize`, and then released once with `LocalFree`.
- Clearing reduces residual plaintext but cannot guarantee erasure of compiler temporaries, register or stack spills, swap, hibernation, crash dumps, debugger snapshots, prior copies, or microarchitectural state. Current-user DPAPI is not a strong boundary against malware already executing as the same user or against administrators.
- DPAPI unprotection establishes only candidate bytes. It does not replace HMAC authentication, generation matching, structural validation, freshness, rollback protection, database correspondence, setup or startup permission, or operational authority. No protected object is persisted in this stage.
- Deterministic malformed-wrapper, protected-key payload, fake-protector, and corrupted real DPAPI inputs fail closed through either native rejection or a later strict application-validation boundary. Candidate key-payload parsing alone grants no HMAC, generation, plaintext, startup, or operational authority.
- This hardening reduces confidence risk around malformed and corrupted protected inputs but does not prove DPAPI or cryptographic security. Replay, rollback, same-user malware, administrator access, persistence, and database correspondence remain unresolved.
- Deterministic authenticated-envelope mutation tests show that the tested arbitrary byte mutations cannot create an authenticated result without a valid recomputed tag. A valid tag still establishes neither logical validity, freshness, current key-generation policy, database correspondence, startup permission, nor operational authority.
- Wrong-key, malformed-length, representative-pattern, full-position, boundary, and retagged-malformed-plaintext corpora retain coarse redacted framing and authentication errors. These tests reduce confidence risk around the implemented boundaries but do not prove cryptographic security.
- Strict parsing fails closed on malformed length, framing, encoding version, declared payload length, application-identifier length, or application-identifier UTF-8. There is no fallback parser, format guessing, trailing-data acceptance, or automatic normalization.
- Successfully parsed values remain untrusted until a separate structural-validation call succeeds, and structural success still does not establish authentication, persistence, provenance, database correspondence, startup permission, or operational authority. Parser errors and parsed-value debug output expose neither encoded content nor complete opaque identifiers.
- Deterministic parser mutation tests reduce confidence risk around malformed inputs, field overlap, canonicality, and panics, but do not prove security. No arbitrary input can create operational authority, and observed parse errors and parsed-value debug output remain redacted.
- The logical contract contains no secrets, paths, personal or sacramental data, passwords, recovery codes, key material, machine identity, Windows user identity, or protection metadata. Full parish, installation, database-key generation, and setup publication identifiers must not appear in logs or debug output; the contract's debug representation redacts them.
- The fixed production path is resolved in Rust beneath the application-owned per-user local application-data directory for `io.github.cltubigon.churchapp`. The Rust-owned startup worker invokes the private guarded read-only connection and validation chain from that root. The distinct explicit setup worker can create the encrypted database and initialize only the minimal V1 metadata/bootstrap contract. General writable opening, migration, recovery, and frontend database authority remain absent.
- Pure persistence paths are joined only beneath caller-supplied synthetic roots. New path wrappers and their aggregate have redacted `Debug` output; the presence facts contain no paths, timestamps, contents, or native errors.
- The protected-wrapper reader rejects empty, below-15-byte, and above-65,550-byte reported lengths before exact-size allocation. It retries interrupted reads, collapses premature EOF and other I/O failures to coarse categories, and rejects any byte observed by its single-byte trailing probe. It retains no native error and exposes no path, contents, or observed length through errors or debug output.
- Unavailable inspection has highest classifier precedence, unexpected entry types fail closed as inconsistent, and any observed stage file is non-authoritative unexpected staging. Conclusive clean absence is only `CleanAbsenceCandidate`; it grants no setup, creation, startup, database, or operational authority.
- The pure publication model describes required evidence-last ordering only. It performs no filesystem inspection or mutation and therefore makes no claim about ACLs, reparse points, volumes, atomic replacement, durability, races, flushing, or any other real filesystem security property.
- The Windows filesystem proof uses deterministic synthetic wrapper bytes only and runs only beneath unique test-owned temporary roots. Stage creation is `CREATE_NEW` with zero sharing; reloads use `GENERIC_READ` with `FILE_SHARE_READ`; initial publication uses only `MOVEFILE_WRITE_THROUGH`. Coarse errors and their `Debug` forms retain no path, native code or text, wrapper bytes, user/SID, volume, or identifier data.
- Existing-file replacement is also executable only in Windows tests. Its native call always supplies a null backup path, flags exactly zero, and null reserved pointers. A failed call captures only a private coarse failure family; raw native codes and text are neither retained nor exposed. No retry, rollback, restoration, or per-file cleanup follows the call; only exact test-root teardown is allowed after assertions.
- Fresh exact-name inspection, rather than the native return or failure family, is authoritative for the observed post-call state. Byte equality and canonical-wrapper validity do not prove ACL, security-descriptor, named-stream, timestamp, or other metadata equality. The success proof additionally requires stage-to-result file-ID continuity and old-active/result identity distinction.
- Stage and active handles are independently reopened and checked as disk files that are neither directories nor reparse points. Handle-reported sizes must remain in 15–65,550 bytes and unchanged across the existing bounded read. Normalized GUID final paths must match the validated test evidence directory and exact fixed filename, and UNC forms are refused. These checks reduce risk but do not prove complete reparse, junction, or TOCTOU resistance.
- The normal-tree hardening tests reject every reparse attribute and every nonzero known or unknown reparse tag, including inconsistent attribute/tag combinations. They use both full `FILE_ID_INFO` object identity and normalized namespace identity, retain directory handles across leaf validation, and require parent/leaf volume-serial and volume-GUID agreement.
- Exactly one link is required only for protected active and staged installation-evidence wrapper leaves. Zero or multiple links fail closed; directories and the future database receive no hard-link policy in this stage.
- A real Windows test fixture now confirms that both authentication-key wrapper names move from one link to two after `std::fs::hard_link`, that the alias shares the full `FILE_ID_INFO` identity and canonical bytes but not the normalized final path or approved exact name, and that hardening returns `HardLinkRejected` before reading or injected mutation. Alias-only removal restores the original identity, bytes, and one-link state. This grants no production filesystem or publication authority.
- A separate Windows-test-only fixture confirms that an exact normalized `installation-evidence` path and a byte-identical canonical wrapper do not establish directory continuity. A retained read-access target handle without delete sharing blocks the ordinary rename attempt; after target and descendant handles close, the original and prebuilt candidate can exchange namespace occupancy through two controlled `std::fs::rename` calls, and full `FILE_ID_INFO` discontinuity rejects the substitute before any continuation.

It does not mix reparse or hard-link objects into the case and makes no production safety claim; intermediate/root substitution, hostile concurrency, production local-volume enforcement and authority, broader host provenance, and removable/network policy remain deferred. The private Windows-test-only non-authoritative local-volume candidate classifier and controlled observations are already implemented.

The same handle's full identity, normalized path, disk-directory/reparse facts, and saved-parent volume relationship remain stable before the call, immediately after it, and after fresh child inspection. Hardening errors and debug output contain no path or UTF-16 content, file ID, volume GUID or serial, native code or text, or wrapper bytes.

The hard-link and single controlled exact-target substitution cases do not establish production path safety, general race resistance, hostile reparse or broader substitution handling, enterprise-profile support, local fixed-volume policy, removable-device or hot-plug safety, or production publication authority.

## Approved production database security policy, guarded handoff, and validation

Carlo explicitly approved this bounded security architecture. The Windows production SQLCipher dependency, private raw-key primitive, metadata-only inspection, guarded read-only handoff, consuming trust-chain transitions, startup authorization, operational activation, Rust-owned application lifecycle, explicit first-time creation, minimal V1 metadata/bootstrap schema, migration safety foundations, verified encrypted SQLCipher migration-backup stage, private recovery-envelope backup verification, C1 custody foundation, C2a adapter, C2b lifecycle/main-thread/real-main-window dispatch, and first-set database, envelope, and manifest-last publication with independent per-artifact fresh verification are current implemented capability. The application retains the activated `OperationalProductionDatabase` only in the internal lifecycle. Migration execution, parish/business schema, normal product reachability and manual ceremony validation, operational portable recovery, complete durable Layer D publication, restore, replacement, retention/deletion, authentication, parish workflows, and general frontend database operations remain absent.

- SQLCipher Community Edition is mandatory for production parish databases, production backups, and production recovery databases. Plain SQLite and encrypted/unencrypted fallback are prohibited. Windows production now depends on exactly `rusqlite = { version = "=0.39.0", default-features = false, features = ["backup", "bundled-sqlcipher-vendored-openssl"] }` under `[target.'cfg(windows)'.dependencies]`. There is no Windows `rusqlite` development dependency and no direct `libsqlite3-sys` dependency. The former test-only dependency state and feasibility proof are historical evidence. Pinned SQLCipher/OpenSSL versions and the lockfile remain release evidence.
- The private Windows-only key-application boundary accepts only `&GenerationBoundDatabaseKey` and a caller-supplied already-open handle. It creates one fixed 67-byte owner containing exact lowercase `x'<64 hex characters>'`, invokes `sqlite3_key` exactly once, treats only `SQLITE_OK` as success, and best-effort zeroizes the owned encoded buffer. The key remains Rust/backend-only: it is not logged, serialized, sent through IPC, exposed to React, or accepted from a Tauri command.
- The production inspector remains metadata-only: it retains parent and database-file proofs and exposes no database-content capability. A separate private `ConnectionLifetimeWriteGuard` deliberately opens the inspected file with native content-read capability using `FILE_READ_ATTRIBUTES | FILE_READ_DATA`, `FILE_SHARE_READ`, `OPEN_EXISTING`, and `FILE_FLAG_OPEN_REPARSE_POINT`, but it exposes no guard handle, file, path, identity, content-read API, raw handle, or database-content capability.
- The guard is identity-matched to the inspected proof before the one SQLite open. SQLite's borrowed main-database Windows handle is retrieved through `SQLITE_FCNTL_WIN32_GET_HANDLE` and identity-matched to the same proof. Raw SQLite and Windows handles never escape.
- The handoff performs exactly one application-level path-based `Connection::open_with_flags_and_vfs(..., "win32")` using `SQLITE_OPEN_READ_ONLY | SQLITE_OPEN_FULL_MUTEX | SQLITE_OPEN_PRIVATE_CACHE | SQLITE_OPEN_NOFOLLOW`. It excludes read-write, create, shared-cache, no-mutex, memory, and URI flags. No-create means no main-database creation, and one attempt means no application retry loop or writable fallback; SQLite internal retries remain engine behavior.
- Before key application the connection receives a five-second busy timeout, disabled extension loading, defensive mode, disabled trusted schema, no-checkpoint-on-close, disabled attach-create and attach-write, and confirmation that the main database is read-only. The existing generation-bound key is applied exactly once; query-only is enabled and verified only afterward.
- Native failures and all returned/logged states disclose no path, key, SQL, PRAGMA, identity, native code, raw SQLite or Windows handle, or raw error chain. Key-application success proves only acceptance of the one key-submission call. It does not prove key correctness, encryption validity, readability, integrity, metadata, correspondence, freshness, startup permission, or operational authority.
- The opaque keyed-but-unvalidated owner retains the `rusqlite::Connection`, guard, and inspection proof as one lifetime unit. Construction-time and normal close failures retain the full unit, and only consuming close or close-retry transitions are exposed. The Rust startup worker is its application-level consumer; no direct frontend database command or IPC operation exists.
- The independent database key is 256 random bits from the Windows OS cryptographic RNG. It is never password-derived, value-derived, or shared with the evidence HMAC key. Its owner is non-`Copy`, has no unrestricted `Clone`, redacts formatting, and best-effort zeroizes owned buffers.
- A dedicated CurrentUser-DPAPI wrapper protects the live database key. Portable recovery uses a separate random recovery key and an authenticated recovery envelope. C1 and private C2a are implemented, but operational duplication, physical separation, rotation, loss handling, and destruction remain future operator/security duties; live-key DPAPI protection does not replace portable recovery policy.
- Metadata fails closed on a missing, duplicate, partial, wrong-class, wrong-length, unsupported, or malformed singleton row. In particular, `permanent_application_identifier` is bounded canonical UTF-8 SQLite `TEXT`, while `database_format_identity` is the existing typed `ApplicationDatabaseFormatIdentity` encoded only as an exactly 16-byte SQLite `BLOB`, directly decoded to that type and compared by exact typed equality. It is never text or a textual, numeric, hashed, prefixed, or fingerprint representation.
- The implemented live adapter uses only `PRAGMA main.application_id`, `PRAGMA main.user_version`, and the fixed explicit 12-column `SELECT` from `main.church_app_database_metadata` with `LIMIT 2`. Both PRAGMAs require exactly one column, exactly one row, SQLite `INTEGER`, signed-32-bit representability, and normal terminal completion. The metadata statement requires 12 columns; it copies the first row into a private owned raw observation before checking for a second row. `LIMIT 2` bounds work while distinguishing zero, exactly one, and more than one row, and no `singleton_id` filter hides additional rows.
- Live storage-class matching is exact and conversion-free: `INTEGER`, raw `TEXT`, `BLOB`, and `NULL` adapt to the existing database-neutral raw values; `TEXT` must pass strict UTF-8; `REAL` fails as `MalformedMetadata`. No cast, `typeof()`, schema introspection, dynamic SQL, arbitrary content query, or duplicate field parser is approved. Temporary headers, raw observations, parsed metadata, and partial validation state are discarded on failure before explicit close.
- Raw SQLite or rusqlite error-message text must never be parsed to infer table absence or schema shape. An absent named relation, missing required column, malformed relation shape, or other failure to prepare/start the fixed query is coarsely `MetadataObservationUnavailable`; normal zero-row completion is `MetadataRowMissing`. This stage makes no physical DDL, constraint, index, trigger, object-kind, or wider-schema claim.
- The live stage exposes exactly `HeaderObservationUnavailable`, `WrongApplicationId`, `MetadataObservationUnavailable`, `MetadataObservationInterruptedOrIncomplete`, `MetadataRowMissing`, `DuplicateMetadataRows`, `MalformedMetadata`, `UnsupportedMetadataContractVersion`, `UnsupportedDatabaseSchemaVersion`, and `UserVersionMismatch` as primary categories. `CloseFailed` is ownership-bearing rather than primary, and processing stops at the first failed stage without collecting or exposing multiple defects.
- Exact typed correspondence covers the permanent application identifier, database-format identity, parish identifier, installation identifier, database-key generation identifier, and setup-publication identifier. Correspondence ignores both generation values; only the later local-anchor freshness boundary may compare them. Evidence-format fields stay evidence-only, and timestamps affect neither correspondence nor freshness authorization.
- The implemented freshness boundary consumes `DatabaseEvidenceCorrespondenceValidatedProductionDatabaseConnection` and exactly one preloaded `NormalizedFreshnessAnchorObservation`, invokes the existing pure classifier once, and advances only on `Fresh`. It performs no anchor loading or database read. The lifecycle then independently re-observes canonical installation evidence, passes that actual value to startup authorization, and performs operational activation only after authorization succeeds.
- Correspondence establishes no rollback resistance. HMAC, DPAPI, timestamps, identity correspondence, and integrity checks do not establish freshness or startup authority.
- The approved production path is the exact application-owned directory and `parish-data.db` on local NTFS. Reparse points, symlinks, junctions, mount traversal, cloud placeholders, hard links, network or removable storage, unstable identity, unexpected sidecars, WAL, and SHM fail closed. Startup never deletes or repairs sidecars. A dedicated database adapter with database-aware race protection is required; evidence-wrapper loading is not a drop-in database hardening implementation.
- Read-only/no-create applies to the main database file. Later SQLite operations may still involve auxiliary-file behavior. `SQLITE_OPEN_NOFOLLOW` is defense in depth rather than the primary Windows reparse guarantee, and query-only is defense in depth rather than the primary read-only guarantee.
- While the verified guard remains open, ordinary Windows filesystem opens requesting incompatible write or delete access to the guarded file object are refused under normal Windows sharing semantics. This is not total external-write prevention: it does not protect against pre-guard mutation, kernel-mode activity, filesystem filters, raw-volume access, privileged bypass, storage or hardware faults, or operating-system/filesystem defects.
- The implemented and accepted readability-and-integrity boundary consumes `ProductionReadOnlyDatabaseConnection` and runs only `PRAGMA cipher_integrity_check` to normal zero-row completion, followed by `PRAGMA main.quick_check(1)` to exactly one complete SQLite `TEXT` value `ok` and normal end-of-stream. No separate readability query exists, and `sqlite_master`, metadata tables, `application_id`, `user_version`, product tables, arbitrary content, and unrestricted SQL remain outside this boundary.
- The exact primary validation categories are `EncryptedDatabaseAuthenticationOrCipherIntegrityFailed`, `SQLiteReadabilityOrIntegrityFailed`, `ValidationUnavailable`, and `ValidationInterruptedOrIncomplete`. They intentionally do not expose an unsupported distinction between wrong key and cipher-page/HMAC failure or between corrupt and unsupported/unreadable SQLite content. SQL or PRAGMA text, cipher-integrity result text, quick-check diagnostic text, paths, keys, identifiers or identities, SQLite/native codes, raw handles, and rusqlite errors or chains are neither retained nor exposed.
- Cipher success requires normal zero-row completion. The first returned cipher row establishes failure without decoding, copying, formatting, retaining, or logging its text; later rows need not be consumed, and the row stream must be dropped or reset before close. Stopping after the first failure row is not an incomplete success because failure is already established.
- Quick-check success requires exactly one text row equal to `ok` followed by normal completion. Zero rows, multiple rows, non-text output, non-`ok` output, stepping errors, interruption, malformed result shape, or premature termination fail closed. The diagnostic value is not exposed. This limited `quick_check` is not full `integrity_check` and does not prove every SQLite invariant; full integrity remains required at separately controlled mutation and recovery boundaries.
- A separate private, consuming full-integrity boundary is implemented from `ReadabilityAndIntegrityValidatedProductionDatabaseConnection` to `FullIntegrityValidatedProductionDatabaseConnection`. It retains the guarded connection lifetime and runs only fixed `PRAGMA main.integrity_check`; success requires exactly one SQLite `TEXT` row exactly equal to `ok` followed by normal completion. Malformed, unavailable, interrupted, incomplete, zero-row, extra-row, non-`TEXT`, and non-`ok` outcomes fail closed. Explicit close and ownership-bearing close retry are preserved. No connection, arbitrary SQL, path, key, metadata, diagnostic text, raw handle, or backend error is exposed.
- The full-integrity boundary is now composed only into the production migration source consumed by the encrypted backup stage. It remains outside ordinary startup, setup, restore, recovery, IPC, and frontend. Ordinary startup remains the accepted `cipher_integrity_check` plus `quick_check(1)` path, and setup remains unchanged.
- No active cancellation API or rusqlite hooks feature is approved for this stage. No validation counts as success without its complete required terminal result. `SQLITE_INTERRUPT`, statement errors, malformed shape, and premature termination map to coarse fail-closed outcomes; active user cancellation remains separately scoped.
- Both checks run sequentially on the same privately owned connection while the existing guard and inspection proof remain retained and query-only, defensive mode, and read-only opening remain active. No explicit SQLite transaction is added and no stronger snapshot guarantee is claimed beyond the guarded same-connection lifetime.
- On validation failure, statement and row-stream state is released before explicit close. Close success returns the primary coarse category. Close failure preserves both that category and an opaque close-retry owner containing the complete connection, guard, and inspection-proof lifetime unit; raw close detail is discarded. There is no automatic repair, header/metadata repair, schema downgrade, journal-mode switch, VACUUM, or cleanup.
- The implemented live stage follows the same lifetime discipline. Every primary failure releases `Rows` and `Statement`, discards all temporary observation and metadata values, then explicitly closes. Close failure retains the same primary category and complete connection/guard/inspection lifetime unit across consuming retries. `LiveMetadataAndHeaderValidatedProductionDatabaseConnection` retains the unchanged lifetime unit plus one owned `DatabaseMetadataContractV1`, but no separate header values; its explicit close discards the contract first, and a failed close retains only the complete lifetime unit.
- Outward `Debug`, `Display`, logs, panic text, IPC, and frontend state for the live stage never expose SQL or PRAGMA text; table or column names; raw rusqlite errors or messages; SQLite codes; `application_id`; `user_version`; metadata versions; identifiers; generations; creation timestamp; canonical application identifier; database-format identity; row values; byte lengths; or failing field index. `DatabaseMetadataContractV1` exposes some non-secret values through its own `Debug`, so live-stage owners, outcomes, and close failures use manual redacted formatting and never delegate to that implementation.
- `cipher_integrity_check` may synchronously scan the whole database with work proportional to database pages. No production database-size ceiling, bounded-latency guarantee, or active-cancellation claim is introduced. The accepted lifecycle runs it in the one blocking startup worker, off the UI/event loop; this does not bound worker duration or eliminate shutdown drain time.
- Initial durability is rollback-journal `DELETE`, `synchronous=FULL`, explicit transactions, `secure_delete=ON`, and `auto_vacuum=NONE`; WAL/SHM and WAL checkpoints are outside the initial policy.
- Setup is the sole creation authority. Filesystem observation, evidence authentication, key recovery, opening, storage integrity, correspondence, freshness, installation classification, application startup authorization, operational activation, and lifecycle ownership remain separate stages. Recovery, restore, migration, rekey, anchor replacement, database replacement, and destructive cleanup each require separate authorization. No generic repair authority exists.

The implemented handoff and consuming typed transitions retain the same connection, guard, and inspection proof through `StartupAuthorizedProductionDatabaseConnection`; operational activation then transfers that ownership into `OperationalProductionDatabase`. Validation and close failures retain only the approved coarse category and required lifetime ownership. Filesystem observation, evidence trust, storage integrity, correspondence, freshness, startup authorization, and activation do not substitute for one another. Errors and lifecycle logs expose no path, SQL or PRAGMA text, validation diagnostic, key, identifier, identity, generation, timestamp, header value, metadata value, DPAPI data, native status, raw handle, raw chain, username, or profile directory. Activation grants no setup, schema-completeness, migration, recovery, backup/restore, replacement, authentication, or business-workflow authority.

### Implemented identity-only correspondence security boundary

### Implemented migration recovery-key custody security boundary

Migration Recovery Key Custody Format Version 1 is a plaintext bearer-secret record. Canonical output is exactly five LF-separated lines, 196 bytes, no terminal newline, with lengths 32/36/36/68/20 and prefix `CHURCH-MIGRATION-RECOVERY-KEY-V1`. It encodes only the recovery-key-generation ID, backup-set ID, 256-bit migration recovery key, and checksum. It contains no parish, installation, schema, path, timestamp, copy-number, operator, or storage-location data.

The exact alphabet is `0123456789ABCDEFGHJKMNPQRSTVWXYZ`, encoded MSB-first without padding. Canonical rendering is uppercase; parsing is ASCII case-insensitive with no Unicode normalization or ambiguous-character aliases, and rejects `I`, `L`, `O`, and `U` in encoded positions. Exact field symbol counts/grouping are `GEN-` 26 as `4-4-4-4-4-4-2`, `SET-` 26 as `4-4-4-4-4-4-2`, `KEY-` 52 as thirteen groups of four, and `CHK-` 13 as `4-4-4-1`.

The checksum takes the first eight bytes of SHA-256 over the exact 105-byte input `ASCII("CHURCH-MIGRATION-RECOVERY-KEY-CHECKSUM") || 0x00 || U16_BE(1) || recovery-key-generation-id[16] || backup-set-id[16] || recovery-key[32]`, then uses the same Base32 alphabet. It is only typo/error detection. It is not authentication, a MAC, password verification, provenance, or restore authority. The recovery-envelope AEAD remains the cryptographic authentication boundary.

The encoded owner contains fixed `[u8; 196]`, is non-`Copy`, non-`Clone`, non-serde, redacted, and zeroizing on drop, with no generic production text/string/raw-byte interface. Parsed/checksum-validated states zeroize secret material.
