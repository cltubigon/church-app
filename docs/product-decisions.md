# Product decisions

## Implemented foundation facts

- **Implemented stack:** Tauri 2, Rust, React, TypeScript, Vite, and npm.
- **Trust boundary:** Rust is trusted; React is presentation and interaction only.
- **Scope:** application shell, placeholder routing, a non-sensitive health command, Rust-only storage-path and storage-identity foundations, pure Rust installation-state decisions, a structural installation-evidence contract, its pure deterministic encoding, strict plaintext parsing, strict authenticated-envelope framing, Rust-owned evidence-authentication keys, operating-system-backed authentication-material generation, pure HMAC-SHA-256 envelope construction and verification, and a pure non-production persistence model.
- **Permanent identity:** production display name `Church App`, application identifier `io.github.cltubigon.churchapp`, version `0.1.0`.
- **Storage-path boundary:** the production database path is resolved only in Rust beneath Tauri's per-user local application-data directory and uses the fixed filename `parish-data.db`.
- **Pure persistence foundation:** Rust owns exact active and publication-stage names, typed path joins beneath caller-supplied synthetic roots, bounded protected-wrapper reading over `Read`, path-free persisted-presence classification, and pure evidence-last publication ordering for initial, evidence-only, and key-generation replacement operations. These are non-operational models only; they do not inspect, create, read, write, publish, replace, or select real files.
- **Windows filesystem binding preflight:** The accepted preflight compile-checks the approved storage-filesystem imports, exact signatures, structures, flags, pointer and length types, and `OwnedHandle` relationships. Those static checks remain alongside the separately scoped test-only runtime proof.
- **Single-wrapper temporary publication proof:** Windows tests now exercise initial no-replace publication for one deterministic synthetic authentication-key wrapper beneath unique test-owned temporary roots. This is test evidence only and adds no production persistence, loading, setup, startup, or operational authority.
- **Existing-file replacement proof:** Windows tests now also exercise one exact null-backup, zero-flag `ReplaceFileW` replacement after independent canonical active/stage validation and ordinary-handle closure, followed by fresh exact-name and file-identity verification. This is test-owned implementation evidence only, not production persistence or operational authority.
- **Normal-tree handle/path hardening proof:** Windows tests validate one ordinary synthetic component chain with retained directory handles, reject-all reparse facts, full `FILE_ID_INFO`, exact normalized volume-GUID components, same-volume checks, a wrapper-only one-link rule, and before/after bounded-read revalidation. This is normal-tree test evidence only and does not establish production path safety.
- **Real hard-link fixture proof:** Separate Windows tests for the active and staged authentication-key wrappers use `std::fs::hard_link` to establish a shared full file identity and canonical bytes at two distinct normalized paths, then prove exact-name and single-link rejection occurs before reading or injected mutation. Removing only the alias restores the original one-link identity and bytes. This is test evidence only and adds no production filesystem or publication authority.
- **Exact evidence-directory substitution test fact:** One Windows-only synthetic fixture observes that a byte-identical canonical wrapper moved into the exact `installation-evidence` path is detected by full directory-identity discontinuity before its injected continuation. This is an observed test fact, not production identity storage, enforcement, repair, persistence, or operational authority.
- **Retained evidence-directory replacement compatibility test fact:** On the observed Windows filesystem, the exact validated `installation-evidence` handle using `GENERIC_READ`, read/write sharing without delete sharing, backup semantics, and open-reparse-point semantics remained open while the accepted one-shot child replacement succeeded and fresh child inspection completed. This is an observed Windows-test fact, not production enforcement or filesystem authority.
- **Local-volume candidate test fact:** On the observed Windows host, a strict handle-derived normalized volume-GUID path combined with the fixed `GetDriveTypeW` category was classified as non-authoritative `LocalFixedCandidate`. This is test evidence only and does not establish production suitability, removable-media assurance, hot-plug assurance, or operational authority.
- **Device-property candidate test fact:** On the observed Windows host, the retained-root-derived volume device opened once with desired access zero and read/write sharing, then accepted one bounded header query and one bounded full `IOCTL_STORAGE_QUERY_PROPERTY` query. The strict descriptor reported non-removable media and an approved candidate bus family, yielding only private `DevicePropertyCandidate`. No hot-plug query ran, and this fact establishes no device non-removability, internal or physical locality, virtual/remote-backing exclusion, durability, production suitability, or application authority.
- **Controlled-host baseline and USB test facts:** Under `Current Windows account, non-elevated session; administrator-group membership not established.`, the Windows 11 baseline beneath the operating-system temporary directory produced the accepted non-authoritative `LocalFixedCandidate` and `DevicePropertyCandidate` results with one drive-type call, one volume open, two property IOCTL calls, zero hot-plug calls, sentinel preservation, and exact-root cleanup. This is not dedicated-standard-account evidence or production approval. Two manually rooted USB attempts ran: the first stopped broadly during hardened child-directory validation, and the accepted diagnostic rerun stopped at `DirectoryAttributeInfoUnavailable` with disposition `Unavailable`. The USB case remained failed and unclassified; no downstream drive-type, local-volume, or device-property classification occurred, and no filesystem or hardware cause was established. Drive-type, volume-open, property-IOCTL, and hot-plug calls were all zero; sentinel verification was `NotReached`; exact-root cleanup was attempted once and succeeded; and the manual leftover-folder check found no entries. No production or operational authority resulted.
- **Current storage limitation:** no production evidence path is resolved and no production directory, evidence file, or database is inspected, created, opened, read, written, migrated, replaced, or connected.
- **Initialization boundary:** ordinary startup leaves a never-initialized installation setup-required and cannot authorize creation. A distinct Rust-only in-memory authorization transition can indicate that a future setup step is permitted, but performs no setup or storage operation.
- **Missing-storage behavior:** an initialized installation whose expected storage is missing fails closed and is not treated as a new installation. Inconsistent or unavailable evidence also fails closed.
- **Installation-evidence contract:** Rust now models and structurally validates the platform-neutral logical evidence fields. Structural success establishes only local contract coherence; it is not authentication, persistence, database cross-checking, startup authority, or production trust.
- **Installation-evidence encoding and parsing:** Version 1 is exactly 164 bytes with a 12-byte framing prefix, a 152-byte payload, fixed offsets, and canonical big-endian integer representation. Strict Rust-only parsing accepts only that exact form and returns a distinct parsed-but-untrusted type. Structural validation remains a separate explicit boundary.
- **Authenticated-envelope framing and authentication:** The approved version-1 envelope is exactly 226 bytes with `CHEVAUTH` magic, envelope version 1, fixed authentication algorithm identifier 1, a distinct nonzero 16-byte authentication-key generation identifier, declared plaintext length 164, the unchanged canonical plaintext, and a complete 32-byte HMAC-SHA-256 tag. Authentication covers exact bytes `0..194`; the tag occupies `194..226` and is excluded from its own computation.
- **Evidence-authentication-material generation:** Rust generates each per-parish 32-byte evidence-authentication key and its nonzero 16-byte generation identifier independently from the operating-system randomness provider. No universal or deterministic key exists. Generation returns only Rust-owned, redacted in-memory material; success is neither persistence nor activation and establishes no current-generation, database, setup, startup, or operational authority.
- **In-memory DPAPI protection:** On Windows, Rust can protect the authentication-key payload and authenticated-evidence envelope as separate opaque objects with classic current-user DPAPI. Calls are non-interactive (`CRYPTPROTECT_UI_FORBIDDEN`) and accept no optional entropy or description. This stage performs no filesystem or registry persistence.
- **Protection limits:** DPAPI success establishes only same-profile local protection or unprotection. HMAC verification and authenticated key-generation matching remain required before plaintext release; DPAPI does not establish freshness, rollback resistance, database correspondence, startup permission, or operational authority.
- **Authentication limits:** Successful authentication establishes only that a holder of the caller-supplied key authenticated the exact envelope prefix. It does not establish freshness, rollback protection, current generation policy, database correspondence, startup authority, or operational installation state.

## Locked future direction (not implemented)

- Desktop-first and offline-capable; Windows 10 and Windows 11 are intended targets.
- Ordinary Church App use may run under the current Windows account, and the process should run in a non-elevated session. Administrator-group membership need not be established for the accepted current-account evidence. A dedicated standard Windows account is optional and recommended for a parish-owned shared workstation, not an ordinary-use prerequisite. Elevation refusal is not yet implemented; this direction does not approve privileged or elevated ordinary operation.
- Production data will operate only from the application-owned per-user local application-data directory.
- Production database creation may occur only through a future explicit first-time setup flow; ordinary startup does not authorize setup and must never silently create a missing database.
- Each future parish database will contain an immutable randomly generated opaque parish identifier. Representation and validation boundaries exist, but generation and persistence do not.
- The accepted future installation-evidence architecture is external protected evidence plus matching identity inside the encrypted database. Neither layer is sole authority; evidence must eventually be authenticated and cross-checked before it can inform operational installation state.
- The implemented authentication tag sits outside the logical evidence record. The in-memory DPAPI layer wraps the authenticated envelope without redefining the logical encoding. Migration between encoding versions will be explicit.
- SQLCipher remains a production-storage candidate, not the selected final engine.
- Local parish data will be authoritative; future central Supabase services will be non-authoritative.
- The public Next.js application and canonical contracts belong in separate repositories.
- The first release direction is English only.
- Schedule timezone: `Asia/Manila`; dates: `MM/DD/YYYY`; times: 12-hour with AM/PM.
- Future primary request statuses are Pending, Scheduled, Completed, and Cancelled.
- The prior visible **Cancellation requested** primary-status indicator rule is superseded: no such primary-status indicator is to be shown.

The implemented initialization work is decision logic only. Parsing establishes no authentication, protection, persistence, provenance, database match, startup authority, or operational trust. These directions do not authorize setup orchestration, persistence, database creation or opening, setup UI, schemas, migrations, authentication, recovery, backup, or product workflows in this repository.
