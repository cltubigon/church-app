## Implemented foundation facts

The current Rust-only boundary independently verifies both published recovery sets and composes them into final keyless Layer D proof. The aggregate transition consumes only `SecondCompleteRecoverySetVerified`; it accepts no fresh custody record or secret-bearing input and repeats no AEAD or SQLCipher verification.

- **Implemented stack:** Tauri 2, Rust, React, TypeScript, Vite, and npm.
- **Trust boundary:** Rust is trusted; React is presentation and interaction only.
- **Scope:** application shell, placeholder routing, a non-sensitive health command, read-only coarse `startup_status`, the narrow `request_first_time_setup` command, Rust-only storage and trust-chain foundations, the guarded production database chain, startup authorization, operational activation, Rust-owned lifecycles, migration safety/custody foundations, independently verified complete first and second recovery sets, and final aggregate Layer D proof. C2b is private, unreachable through normal product interaction, and manually unvalidated. Explicit first-time setup and the minimal production V1 metadata/bootstrap schema are implemented. The product still has no migration execution, parish/business schema, operational portable recovery, Layer D lifecycle composition, restore, retention/deletion, authentication, parish workflow, or general writable database interface and is not launch-ready.
- **Permanent identity:** production display name `Church App`, application identifier `io.github.cltubigon.churchapp`, version `0.1.0`.
- **Storage-path boundary:** the production database path is resolved only in Rust beneath Tauri's per-user local application-data directory and uses the fixed filename `parish-data.db`.
- **Pure persistence foundation:** Rust owns exact active and publication-stage names, typed path joins beneath caller-supplied synthetic roots, bounded protected-wrapper reading over `Read`, path-free persisted-presence classification, and pure evidence-last publication ordering for initial, evidence-only, and key-generation replacement operations. These are non-operational models only; they do not inspect, create, read, write, publish, replace, or select real files.

Those static checks remain alongside the separately scoped test-only runtime proof.

- **Current storage limitation:** the Rust-owned startup worker invokes the implemented read-only observation, loading, guarded connection, validation, authorization, and operational-activation chain beneath the fixed per-user application-local-data root. The separate explicit setup worker can create only the encrypted production database and minimal V1 metadata/bootstrap contract. The separate explicit first-time setup lifecycle begins only from the accepted `NeverInitialized` path through its narrow request command. Successful setup ends in restart-required, never same-process `Ready`; a fresh process must pass the ordinary startup trust chain.
- **Missing-storage behavior:** an initialized installation whose expected storage is missing fails closed and is not treated as a new installation. Inconsistent or unavailable evidence also fails closed.
- **Installation-evidence contract:** Rust now models and structurally validates the platform-neutral logical evidence fields. Structural success establishes only local contract coherence; it is not authentication, persistence, database cross-checking, startup authority, or production trust.
- **Installation-evidence encoding and parsing:** Version 1 is exactly 164 bytes with a 12-byte framing prefix, a 152-byte payload, fixed offsets, and canonical big-endian integer representation. Strict Rust-only parsing accepts only that exact form and returns a distinct parsed-but-untrusted type. Structural validation remains a separate explicit boundary.
- **Authenticated-envelope framing and authentication:** The approved version-1 envelope is exactly 226 bytes with `CHEVAUTH` magic, envelope version 1, fixed authentication algorithm identifier 1, a distinct nonzero 16-byte authentication-key generation identifier, declared plaintext length 164, the unchanged canonical plaintext, and a complete 32-byte HMAC-SHA-256 tag. Authentication covers exact bytes `0..194`; the tag occupies `194..226` and is excluded from its own computation.
- **Evidence-authentication-material generation:** Rust generates each per-parish 32-byte evidence-authentication key and its nonzero 16-byte generation identifier independently from the operating-system randomness provider. No universal or deterministic key exists. Generation returns only Rust-owned, redacted in-memory material; success is neither persistence nor activation and establishes no current-generation, database, setup, startup, or operational authority.
- **In-memory DPAPI protection:** On Windows, Rust can protect the authentication-key payload and authenticated-evidence envelope as separate opaque objects with classic current-user DPAPI. Calls are non-interactive (`CRYPTPROTECT_UI_FORBIDDEN`) and accept no optional entropy or description. This stage performs no filesystem or registry persistence.
- **Protection limits:** DPAPI success establishes only same-profile local protection or unprotection. HMAC verification and authenticated key-generation matching remain required before plaintext release; DPAPI does not establish freshness, rollback resistance, database correspondence, startup permission, or operational authority.
- **Authentication limits:** Successful authentication establishes only that a holder of the caller-supplied key authenticated the exact envelope prefix. It does not establish freshness, rollback protection, current generation policy, database correspondence, startup authority, or operational installation state.

## Carlo-approved production database foundation, guarded handoff, and validation

Carlo explicitly approved the bounded production database and evidence-correspondence architecture package recorded below, including the corrected database-format identity encoding. The architecture has crossed the guarded database and migration safety foundations, custody foundations, independently complete-set-verified first and second digital recovery sets, and final aggregate Layer D proof. Engine selection, setup authority, startup authority, migration authority, each validation gate, operational activation, envelope verification, custody foundation, normal product reachability, manual ceremony validation, restore, and final release approval remain distinct decisions. The repository still has no migration execution, parish/business schema, operational portable recovery, Layer D lifecycle composition, restore, rekey, recovery, retention/deletion, authentication, parish workflow, or general frontend database operation.

Delegated architecture and security decisions accepted as part of Carlo's package approval are the read-only/no-create startup inspection semantics, exact correspondence and lineage rules, diagnostic-only timestamps, path restrictions, error redaction, rollback-journal and durability policy, and separation of setup, startup, migration, recovery, and destructive authority.

- **Production engine and dependency gate:** SQLCipher Community Edition is selected. Plain SQLite is prohibited for production parish databases, production backups, and production recovery databases. Windows production now depends on exactly `rusqlite = { version = "=0.39.0", default-features = false, features = ["backup", "bundled-sqlcipher-vendored-openssl"] }` under `[target.'cfg(windows)'.dependencies]`, with no Windows `rusqlite` development dependency and no direct `libsqlite3-sys` dependency. The earlier feasibility module and former development-dependency state are historical test-only evidence. This promotion does not itself open or authorize a production database. SQLCipher/OpenSSL versions and the lockfile remain required release evidence; final release approval has not been granted by this gate.
- **Raw-key primitive gate:** the private Windows-only `sqlcipher_database_key_application` module is registered from Rust and has no public, Tauri, frontend, or IPC surface. Its primitive accepts only `&GenerationBoundDatabaseKey` plus a caller-supplied already-open handle, creates one fixed 67-byte lowercase `x'<64 hex characters>'` owner, invokes `sqlite3_key` exactly once, accepts only `SQLITE_OK`, and exposes only `DatabaseKeyApplicationError::Failed` on failure. It does not itself open, create, select, query, inspect, mutate, rekey, or close a database. The guarded handoff remains its only application-level caller; the lifecycle reaches it only through that handoff.
- **Guarded connection-handoff gate:** after existing metadata-only file inspection, a separate private connection-lifetime guard is identity-bound to the inspected proof. The implementation makes exactly one application-level path-based `Connection::open_with_flags_and_vfs(..., "win32")` call with `SQLITE_OPEN_READ_ONLY | SQLITE_OPEN_FULL_MUTEX | SQLITE_OPEN_PRIVATE_CACHE | SQLITE_OPEN_NOFOLLOW`, identity-binds SQLite's borrowed main-database Windows handle to the same proof, applies the connection-hardening policy, applies the generation-bound key exactly once, and only then enables and verifies query-only. The returned owner is opaque and keyed-but-unvalidated; it carries the connection, guard, and proof together and exposes only consuming close or close-retry transitions. The Rust startup worker consumes it through the fixed later stages; the handoff alone grants no startup authority.
- **Supported production baseline:** Windows 10 x64 and Windows 11 x64, local NTFS, non-elevated standard-user operation, and CurrentUser DPAPI. Windows ARM64, 32-bit Windows, ReFS, removable or network storage, Wine, Windows Server, and compatibility layers are unsupported until separately approved.
- **Database key:** one independent random 256-bit database key generated by the Windows OS cryptographic RNG. It is never password-derived, never derived from parish, installation, evidence, device, or user values, and never shared with the evidence HMAC key. Secret owners must not implement `Copy` or expose unrestricted `Clone`; formatting is redacted and owned secret buffers receive best-effort zeroization. A dedicated CurrentUser-DPAPI wrapper protects the live key. Portable recovery uses a separate random recovery key and authenticated recovery envelope; C1, C2a, and private C2b lifecycle dispatch are implemented, while normal product reachability, manual ceremony validation, operational duplication, physical separation, rotation, loss handling, and destruction remain future operator/security responsibilities.
- **Metadata contract:** version 1 is exactly one canonical non-null row in the singleton table `church_app_database_metadata`; missing, duplicate, partial, wrong-storage-class, wrong-length, unsupported, or malformed values fail closed. Initial database schema version is 1.
- **SQLite headers:** `application_id = 0x43484150`; `user_version` mirrors the validated supported metadata `database_schema_version`, and metadata is authoritative. A wrong fixed application ID is `WrongApplicationId`; a supported validated metadata schema version that differs from `user_version` is `UserVersionMismatch`; correctly represented unsupported metadata versions retain their dedicated unsupported categories; representation defects are malformed. No automatic repair, assignment, normalization, or fallback exists.
- **First business-schema version:** the implemented metadata/bootstrap source is `database_schema_version = 1`. The approved first business target is `database_schema_version = 2`, and version 2 means exactly the approved `service_requests`, `request_schedule_occurrences`, and `request_cancellation_reviews` physical contract below and nothing broader. Target `metadata_contract_version` remains 1, target SQLite `user_version` is 2, `application_id` remains `0x43484150`, and `ApplicationDatabaseFormatIdentity` remains the existing identity. Compatibility is 1 -> 2 only; there is no generic `unsupported -> 2` migration rule, and versions newer than 2 are unsupported and downgrade-refused. This assignment does not implement schema 2 or authorize migration.
- **Correspondence and freshness:** the implemented and accepted identity-only correspondence adapter invokes the existing pure classifier exactly once for exact typed equality of permanent application identifier, application database-format identity, parish identifier, installation identifier, database-key generation identifier, and setup-publication identifier. It ignores installation generation and recovery/replacement generation while retaining both unchanged for freshness. Evidence-format identity/version and database/evidence timestamps cannot authorize freshness. The implemented freshness boundary consumes the correspondence owner plus exactly one preloaded `NormalizedFreshnessAnchorObservation`, reuses the pure freshness classifier exactly once, advances only on `Fresh`, and retains no anchor in its success owner.
- **Implemented readability-and-integrity gate:** the consuming transition starts from `ProductionReadOnlyDatabaseConnection` and runs only `PRAGMA cipher_integrity_check` to normal zero-row completion, followed by `PRAGMA main.quick_check(1)` to exactly one complete SQLite `TEXT` value `ok` and normal end-of-stream. No separate readability probe exists; the limited quick check establishes SQLite-level readability. The gate does not query `sqlite_master`, metadata tables, `application_id`, `user_version`, product tables, or arbitrary content, and it exposes no unrestricted SQL. Success returns `ReadabilityAndIntegrityValidatedProductionDatabaseConnection`.
- **Implemented live metadata and header gate:** the consuming transition starts from `ReadabilityAndIntegrityValidatedProductionDatabaseConnection`, strictly observes `PRAGMA main.application_id`, requires exact `0x43484150`, strictly observes `PRAGMA main.user_version`, executes only the fixed explicit 12-column metadata query with `LIMIT 2`, copies the first row before the second step, adapts exact SQLite storage classes with strict UTF-8, calls the existing `RawDatabaseMetadataRow::parse()` and `validate_structure()`, and requires `user_version` agreement with the supported metadata schema version. Success returns `LiveMetadataAndHeaderValidatedProductionDatabaseConnection` retaining the unchanged lifetime unit and one owned `DatabaseMetadataContractV1`.
- **Readability-and-integrity failures:** that gate has exactly four primary coarse categories: `EncryptedDatabaseAuthenticationOrCipherIntegrityFailed`, `SQLiteReadabilityOrIntegrityFailed`, `ValidationUnavailable`, and `ValidationInterruptedOrIncomplete`. Wrong key is not separated from cipher-envelope/HMAC failure, and corrupt SQLite content is not separated from unsupported or unreadable SQLite representation. Result text, SQL/PRAGMA text, native codes, and raw errors are never exposed. A validation close failure preserves the already determined primary category together with an opaque close-retry owner holding the complete connection, guard, and inspection proof.
- **Readability-and-integrity completion and cancellation:** no active cancellation API or rusqlite hooks feature is approved for that stage. No check succeeds without its complete terminal result. The first cipher result row already proves failure and may end row consumption after the stream is dropped or reset; a cipher success requires clean zero-row completion. Quick-check zero/multiple/non-text/non-`ok` results, statement errors, interruption, malformed shape, or premature termination fail closed. Full integrity checks remain reserved for controlled backup acceptance, staged restore, migration, rekey/key replacement, journal recovery, database replacement, diagnostics, and abnormal-interruption recovery.
- **Implemented private full-integrity capability:** the consuming transition starts from `ReadabilityAndIntegrityValidatedProductionDatabaseConnection`, retains the guarded connection lifetime, runs only fixed `PRAGMA main.integrity_check`, and advances to `FullIntegrityValidatedProductionDatabaseConnection` only for exactly one SQLite `TEXT` row exactly equal to `ok` followed by normal completion. Malformed, unavailable, interrupted, incomplete, zero-row, extra-row, non-`TEXT`, and non-`ok` outcomes fail closed. Explicit close and ownership-bearing close retry are preserved. The boundary exposes no connection, arbitrary SQL, path, key, metadata, diagnostic text, raw handle, or backend error. Later implementation composes it only into the migration source consumed by the encrypted backup stage; ordinary startup, setup, restore, recovery, IPC, and frontend remain unchanged.
- **Whole-file workload acceptance:** `cipher_integrity_check` may synchronously scan the entire database with work proportional to database pages. This gate introduces no production database-size ceiling and makes no bounded-latency or active-cancellation claim. The accepted lifecycle runs the whole synchronous chain in one Rust blocking worker, off the UI/event loop; this does not bound worker duration or eliminate shutdown drain time.
- **Validation connection and authority:** both checks run sequentially on the same privately owned connection while the existing guard, inspection proof, query-only setting, defensive mode, and read-only opening remain active. No explicit SQLite transaction or stronger snapshot guarantee is added. Success is possession of a new opaque validated owner retaining the same lifetime unit and exposing only consuming close and later separately approved fixed consuming transitions. It establishes no metadata table existence, metadata row validity, SQLite `application_id`, SQLite `user_version`, schema-contract validity, database/evidence correspondence, freshness, startup/setup authority, migration authority, recovery authority, backup/restore authority, or operational database use.
- **Path, transaction, and authority policy:** the fixed `parish-data.db` must be in the exact application-owned production directory on local NTFS. Reparse points, symlinks, junctions, mount traversal, cloud placeholders, hard links, network paths, removable storage, unexpected sidecars, WAL, and SHM fail closed. Initial mode is rollback-journal `DELETE`, `synchronous=FULL`, explicit transactions, `secure_delete=ON`, and `auto_vacuum=NONE`, with no automatic journal switching, VACUUM, cleanup, or repair. Setup alone may create database artifacts. Ordinary startup creates none. Migration, recovery, restore, rekey, anchor or database replacement, and destructive cleanup each require separate explicit authority; no generic repair authority exists.

### Implemented live-observation decisions

- **Fixed scope and row count:** the transition strictly observes `PRAGMA main.application_id`, fails immediately on a complete wrong value, then strictly observes `PRAGMA main.user_version`, and finally executes the explicit 12-column query from `main.church_app_database_metadata` with `LIMIT 2`. - **Canonical primary taxonomy:** exactly `HeaderObservationUnavailable`, `WrongApplicationId`, `MetadataObservationUnavailable`, `MetadataObservationInterruptedOrIncomplete`, `MetadataRowMissing`, `DuplicateMetadataRows`, `MalformedMetadata`, `UnsupportedMetadataContractVersion`, `UnsupportedDatabaseSchemaVersion`, and `UserVersionMismatch`. `CloseFailed` is an ownership-bearing result, not a primary category.

The implementation must not infer a table-specific state by parsing raw SQLite or rusqlite error messages. A successfully started fixed query that normally completes with zero rows is separately `MetadataRowMissing`.
- **Version and malformed rules:** a correctly represented `metadata_contract_version` other than 1 is `UnsupportedMetadataContractVersion`; a correctly represented `database_schema_version` other than 1 is `UnsupportedDatabaseSchemaVersion`; wrong storage class, invalid UTF-8, or parse-range failure is `MalformedMetadata`. - **First-failed-stage precedence:** application-ID observation unavailable; wrong application ID; user-version observation unavailable; metadata preparation/query-startup unavailable; metadata stepping interruption or incomplete terminal state; missing row; duplicate rows; malformed storage class, UTF-8, parse, or non-version structural state; unsupported metadata contract version; unsupported database schema version; remaining structural invalidity as malformed; user-version mismatch. Processing stops at the first failure and neither collects nor exposes multiple defects.
- **Success and close ownership:** `LiveMetadataAndHeaderValidatedProductionDatabaseConnection` privately retains only the unchanged `ConnectionLifetimeOwner` and one owned `DatabaseMetadataContractV1`; successful validation does not retain header values separately. It exposes consuming explicit close and later separately approved fixed consuming transitions only. On primary failure, close failure preserves the category and complete connection/guard/inspection unit across consuming retries. Closing the successful owner first discards its metadata contract; a failed close retains only the complete lifetime unit.
- **Placement and authority:** implementation resides in a sealed private child module beneath `production_database_connection_handoff`, without widened visibility, a generic connection callback, or a crate-root sibling bridge. Production only reads the already-existing named relation; test-only synthetic schema/header construction grants no production schema, header-mutation, migration, repair, normalization, correspondence, freshness, startup, setup, recovery, backup/restore, replacement, or operational authority.

### Implemented migration recovery-envelope decisions

- **Implemented proof boundary:** `VerifiedEncryptedProductionDatabaseMigrationBackupStage` proves the exact full-integrity source was copied to an encrypted SQLCipher stage under the same production database key, independently passed cipher integrity and full SQLite integrity, exactly matched source metadata/headers, established ciphertext at rest, retained the unchanged source, and retained migration authorization bound to it. Subsequent private transitions independently publish the second directory's fixed database from the original retained verified source, its fixed envelope from the retained original verified envelope, and its fixed manifest last from freshly reconstructed original trusted source facts. Each uses create-new, explicit flush/close, independent reopen, fresh hardened verification, and predecessor/source/destination continuity checks. `SecondCompleteRecoverySetVerified` then consumes that published predecessor plus one freshly owned custody-record re-entry and proves fresh exact layout, fresh artifact/source correspondence, actual fresh-envelope AEAD authentication, recovered-key SQLCipher verification of the second database, explicit verifier close, and final continuity/layout revalidation. Failure retains only safely representable ownership, with no cleanup, deletion, repair, overwrite, or resume. Final two-set success and the private native-selection primitive are implemented; lifecycle integration, normal product reachability, restore, migration execution, and stronger namespace/directory durability remain unimplemented.

- Exactly two physically distinct, physically disconnectable external recovery devices are required. Each must be distinct from the live Church App production-storage device and from the other recovery device. An eligible USB flash drive or external SSD may qualify; a second partition, volume, directory, mount point, or drive letter on the same physical device does not.
- Each device contains one independently selected, validated, published, freshly reopened, and verified complete digital recovery set. One set consists only of the exact encrypted SQLCipher migration-backup bytes, the exact existing recovery-envelope bytes, and one non-secret manifest used as bounded inventory and publication commit marker. A paper copy is not part of a Layer D digital set, and file presence alone is not completeness.
- The two digital sets are replicas of one logical backup set: identical encrypted-backup bytes, identical recovery-envelope bytes, and the same migration-backup-set identifier. Set 2 is published from the retained verified source, not copied from set 1. Layer D creates no second recovery key, backup-set identifier, recovery envelope, or encrypted backup generation.
- The two already-required verified paper copies remain a separate custody layer. Both stay separate from both digital recovery devices and from each other. Either valid paper copy may recover either valid digital set; no permanent one-to-one paper/device pairing exists, and Church App does not claim proof of later physical separation.
- Publication is create-new, no-replace, no silent merge, no overwrite, no automatic repair, no automatic deletion, and no partial-publication resume. An incomplete or conflicting destination fails closed. A retry requires a newly selected suitable destination; partial artifacts remain for later separately authorized handling.
- **Recovery-volume selection and filesystem:** the implemented private Windows-native picker accepts one existing filesystem folder through `IFileOpenDialog`, but creates selection authority only when `GetVolumeNameForVolumeMountPointW` recognizes that exact selected item as a volume mount-point root and the result passes the existing canonical volume-GUID-root parser. Arbitrary descendants, ancestor walking, and containing-volume normalization are not accepted. It creates only the opaque selection owner and performs no NTFS, USB, hotplug, separation, capacity, publication, lifecycle, or IPC work. The implemented private retained-root authority then requires the opened handle's normalized final path to be exactly `\\?\Volume{GUID}\`, requires the hardened retained directory identity/facts to remain valid, and requires `GetVolumeInformationByHandleW` to report NTFS. First-generation recovery volumes are NTFS only; exFAT is deferred, FAT32 is categorically rejected, and every other, unknown, malformed, or unavailable filesystem observation fails closed.
- **Fixed child:** the exact child name beneath each selected volume root is `church-app-recovery-set`. Unrelated files elsewhere on the volume are allowed. Any pre-existing exact or ASCII-case-conflicting child is a conflict: Church App never adopts, merges, resumes, repairs, overwrites, renames, or automatically deletes it. The private boundary creates set 1 then set 2 with create-new semantics and retains hardened authority to each new child; set-2 failure preserves set 1 without rollback.
- The application-local encrypted source stage remains retained after zero, one, and two complete digital sets. Layer D has no deletion authority; future retention/deletion belongs only to Layer F.
- The first and second digital recovery sets are each independently complete-set verified, and the private keyless final aggregate capability is implemented. It proves only that both sets were independently published and verified, both still correspond to the same retained logical source, required separation and root/child continuity checks succeeded at final composition time, and paper custody had already completed. It authorizes no migration execution, writable ownership, schema mutation, restore, replacement, retention, deletion, or cleanup, and it does not prove later separation or media availability. Layer D lifecycle composition remains unimplemented.
- Recovery Set V1 uses exactly `parish-data.db`, `migration-recovery-envelope-v1.bin`, and `recovery-set-v1.manifest`. These fixed names are neither operator input nor encoded fields and admit no suffix, alias, localization, case variation, arbitrary filename, or path. The manifest is deterministic non-secret inventory and the publication commit marker, never a cryptographic trust root, authenticity proof, migration/restore/publication authority, or substitute for complete Layer D verification.
- Recovery Set Manifest Format Version 1 is locked at exactly 98 bytes: exact `CHLDRSM\0` magic in `0..8`; big-endian `u16` version 1 in `8..10`; raw 16-byte migration backup-set identifier in `10..26`; big-endian `u64` database byte length in `26..34`; raw 32-byte complete-database SHA-256 in `34..66`; and raw 32-byte complete-envelope SHA-256 in `66..98`. It has no length field, trailing data, reserved/padding/flags/extensions, optional or variable fields, delimiters, terminators, negotiation, or fallback.
- Parsing yields `ParsedUntrustedRecoverySetManifestV1` and has exactly `WrongTotalLength`, `WrongMagic`, and `UnsupportedVersion`. Structural validation, in identifier-then-length order, has exactly `InvalidBackupSetIdentifier` for an all-zero identifier and `InvalidDatabaseByteLength` outside `512..=281_474_976_579_584`; digest bytes have no structural rejection. Only validated `RecoverySetManifestV1` canonically encodes, and all accepted valid bytes satisfy `encode(validate(parse(bytes))) == bytes` exactly.
- The manifest implicitly inventories Migration Recovery Envelope Format V1 under its fixed name and exact 182-byte length; those facts are not duplicated as fields. Parsing/validation/encoding performs no hashing, comparison, I/O, envelope parsing, database operation, allocation authorization, or authority construction. Normal formatting exposes neither complete identifiers/digests nor manifest bytes, database length, attacker-controlled values, paths, or device identity. The private dependency-free pure Rust codec and focused deterministic codec tests are implemented. The crate-private trusted constructor from a canonical identifier, `u64` length, and two `[u8; 32]` digests is also implemented and preserves the locked length range and all format/taxonomy/authority limits.
- The keyless `RecoveryKeyCustodyVerifiedProductionDatabaseMigrationBackup` now provides a private borrowed manifest-preparation boundary. It derives the identifier only from the retained verified envelope's strict parser/accessor path; freshly observes and SHA-256 hashes the identity-checked retained stage with the 64 KiB bounded buffer, checked byte counting, before/after lengths, and equality of both lengths with streamed count; reuses that observation primitive for the existing stage-digest path; and freshly hashes the exact retained 182-byte envelope. Success and the fixed redacted failures `SourceObservationUnavailable`, `StageIdentityUnavailableOrChanged`, and `ManifestConstructionRejected` preserve the original owner.
- Manifest construction creates no recovery set, migration authorization, publication authority, or restore authority. The private native picker, retained-volume, device-separation, exact-root, capacity, and fixed-child prerequisites are implemented under their existing constraints. First-set and second-set publication, recovered-key verification, exact final three-entry layout proof, independent complete-set verification, and the final aggregate keyless Layer D proof are implemented. Each exact 98-byte manifest is freshly parsed and structurally validated, canonically re-encoded, and checked against freshly prepared trusted-source bytes; the second manifest is reconstructed independently rather than read or copied from set 1. The second complete-set owner additionally proves fresh artifact/source correspondence, actual fresh-envelope AEAD authentication under a newly owned custody-record re-entry, recovered-key SQLCipher verification of the second database, explicit verifier close, and final continuity/layout revalidation. The final transition consumes only `SecondCompleteRecoverySetVerified` and returns the private keyless `TwoCompleteRecoverySetsVerifiedProductionDatabaseMigrationBackup`. Partial artifacts remain without cleanup or resume. Lifecycle composition, normal product reachability, restore, retention/deletion, and migration execution remain unimplemented.
- Rejected manifest alternatives remain JSON, YAML, TOML, XML, CBOR, MessagePack, protobuf, serde-driven serialization, textual UUID, hex/Base64 digests, variable/operator filenames, paths, timestamps, copy/set/generation/device/volume/operator/parish/installation identity fields, database-key-generation/setup-publication identifiers, self-digest, MAC/signature, reserved or extension space, optional fields, flags, declared manifest/envelope lengths, separate envelope version, permissive unknown versions, and trailing-data acceptance.

- **Loader contract:** the anchor loader proves bounded, stable selection and validation of the current active wrapper pair, not absolute historical continuity. Disappearance without replacement is rejected; after recreation the loader may reject or may succeed only with the fully validated current recreated pair. Stale or mixed-pair success is forbidden. ## First business-schema product and physical-design contract (not implemented)

This is the canonical record for the final approved product behavior and physical design. The headings below deliberately distinguish PRODUCT-LOCKED behavior, APPROVED PHYSICAL DESIGN, FUTURE RUST TRANSACTION RESPONSIBILITY, and STILL UNIMPLEMENTED work. The business scope is exactly `ServiceRequest`, `RequestScheduleOccurrence`, and `RequestCancellationReview`. No fourth business entity, lookup table, generic workflow engine, generic audit/history/event-sourcing or soft-delete system, person/parishioner table, or permanent/sacramental-record entity is approved.

### PRODUCT-LOCKED behavior

- Fixed service categories are Baptism, Confirmation, Wedding/Marriage, Burial/Funeral, and First Communion. Wedding/Marriage and Burial/Funeral are each one category. There is no configurable service catalog.
- Primary request states are `Pending`, `Scheduled`, `Completed`, and `Cancelled`. Every request is created as `Pending`. The only transitions are `Pending -> Scheduled`, `Pending -> Cancelled`, `Scheduled -> Completed`, and `Scheduled -> Cancelled`; there is no reopening, reverse transition, or reactivation.
- Cancellation review is separate from primary status. An unresolved review leaves the primary status unchanged and has no independent schedule effect. Approval changes a `Pending` or `Scheduled` request to `Cancelled`; rejection leaves status unchanged. Resolved reviews remain stored, and rejection permits a later review request.
- Only occurrences whose parent request is `Scheduled` occupy schedule slots. `Pending`, `Completed`, and `Cancelled` requests do not occupy slots. Pending occurrences are allowed as drafts. Completion or cancellation releases occupancy without deleting occurrences; occurrences remain historical facts.
- Rescheduling a `Scheduled` request updates its existing occurrence row in place while the request remains `Scheduled`. Old-slot release, new-slot conflict detection, and the update are one atomic operation. There is no schedule-history entity.
- Conflict is exact equality of local date and local time in one shared parish schedule. Location does not affect conflicts, and pending cancellation does not release a slot. Duration, end time, interval overlap, clergy/resource/capacity, and resource-scoped conflicts remain unapproved.
- Baptism, Confirmation, Wedding/Marriage, and First Communion each require exactly one primary occurrence before scheduling. Burial/Funeral requires at least one of Funeral or Burial; Funeral alone, Burial alone, or both are valid, while neither is invalid. At most one occurrence of each kind may exist per request.
- Location may be absent while a request is pending. Wedding/Marriage and First Communion require a non-empty final occurrence location before scheduling and throughout `Scheduled`. Location is optional for Baptism, Confirmation, Funeral, and Burial; Funeral and Burial may use different locations. There is no location catalog.
- The schedule timezone is `Asia/Manila`. Persisted schedule facts use minute precision. `MM/DD/YYYY` and 12-hour AM/PM are presentation only.
- The requester is a request-local snapshot of full name, mobile/phone, and optional email, not a durable person identity. Normalized people, family/household and role relationships, permanent or sacramental records, and completion-driven record creation remain deferred.

### APPROVED PHYSICAL DESIGN

- The exact tables are `service_requests`, `request_schedule_occurrences`, and `request_cancellation_reviews`. All three are `STRICT`, use `id INTEGER PRIMARY KEY`, and do not use `WITHOUT ROWID`. The ID is internal database identity only; raw database IDs are not approved as frontend or IPC authority, whose future design remains separate.
- `service_requests` contains `id`, `service_category`, `status`, `requester_full_name`, `requester_phone`, nullable `requester_email`, and `created_at`.
- `request_schedule_occurrences` contains `id`, `service_request_id`, `occurrence_kind`, `scheduled_local_date`, `scheduled_local_time`, and nullable `location`. It does not duplicate service category.
- `request_cancellation_reviews` contains `id`, `service_request_id`, `disposition`, `requested_at`, and nullable `resolved_at`.
- Persisted service codes are exactly lowercase ASCII `baptism`, `confirmation`, `wedding_marriage`, `burial_funeral`, and `first_communion`. Persisted request-status codes are `pending`, `scheduled`, `completed`, and `cancelled`. Persisted occurrence-kind codes are `primary`, `funeral`, and `burial`. Persisted cancellation dispositions are `pending`, `approved`, and `rejected`. There are no lookup tables.
- `status` and `disposition` are required and have no SQLite default. Rust must bind `pending` explicitly when creating a request or cancellation review.
- `scheduled_local_date` is canonical `YYYY-MM-DD` `TEXT`; the database checks shape only and Rust checks actual Gregorian validity. `scheduled_local_time` is canonical 24-hour `HH:MM` `TEXT`; the database checks shape plus hour/minute ranges. No seconds or per-row timezone column exists.
- `created_at`, `requested_at`, and `resolved_at` are non-negative UTC Unix milliseconds stored as SQLite `INTEGER`. `resolved_at` is `NULL` exactly while disposition is `pending` and non-`NULL` for `approved` or `rejected`. It need not be greater than or equal to `requested_at`, because wall-clock correction may occur. Deterministic chronology may use `(timestamp, id)`.
- `requester_full_name` has a 200-Unicode-character maximum and `requester_phone` a 32-character maximum; both are required. Optional `requester_email` has a 254-character maximum. Optional `location` has a 256-character maximum. Optional values use `NULL` when absent; an empty string is invalid. Database checks enforce length 1 through the maximum when present and no leading or trailing ASCII spaces. They do not replace Rust validation.
- Both `service_request_id` columns reference `service_requests(id)` with `ON UPDATE RESTRICT ON DELETE RESTRICT`. No deletion workflow is approved. These declarations do not provide enforcement until a separately designed future writable connection enables and verifies foreign-key enforcement; current startup connection policy remains unchanged.
- `UNIQUE(service_request_id, occurrence_kind)` enforces at most one occurrence of each kind per request. A partial unique index on cancellation reviews enforces unique `service_request_id` where `disposition = 'pending'`. Resolved approved/rejected reviews remain retained.
- The only approved additional indexes are `service_requests(status, created_at, id)`, `request_schedule_occurrences(scheduled_local_date, scheduled_local_time, id)`, `request_cancellation_reviews(service_request_id, requested_at, id)`, and pending-only `request_cancellation_reviews(requested_at, id)`. There is no unique schedule-slot constraint and there are no speculative indexes.
- No triggers are approved. Row-level checks constrain the persisted code sets, text bounds/ASCII-space rules, non-negative timestamps, resolved-time nullability, date shape, and time shape/ranges.
- No generic `updated_at`, `deleted_at`, status-change, audit, or other timestamps are added. No schedule-history, status-history, audit, event, person, service-catalog, location-catalog, or sacramental-record table is added.

### FUTURE RUST TRANSACTION RESPONSIBILITY

- Rust trims required text and rejects an empty result. It represents absent optional email/location as `NULL` and rejects empty present values, NUL, and disallowed control characters without aggressive case-folding or destructive normalization.
- Sealed Rust mutation APIs enforce lifecycle transitions in explicit write transactions. The recommended compare-and-set update supplies request ID, expected source, and target and succeeds only when exactly one row changes. Triggers are not used.
- Before `Pending -> Scheduled`, Rust enforces service/occurrence compatibility and cardinality: `primary` only for Baptism, Confirmation, Wedding/Marriage, and First Communion; `funeral` and/or `burial` only for Burial/Funeral. A Burial/Funeral `primary`, or `funeral`/`burial` for another service, is invalid.
- Rust enforces category-dependent location requirements, actual Gregorian date validity, and conflict checks against another occurrence at the exact date/time whose parent request is currently `scheduled`.
- Scheduling and rescheduling are atomic Rust write transactions. Rescheduling releases the old slot, checks the new slot, and updates the existing occurrence together.
- Cancellation approval is one sealed Rust-owned write transaction: require the review still `pending`; require parent status `pending` or `scheduled`; update the parent to `cancelled`; update the review to `approved`; set `resolved_at`; require exactly one affected row for each mutation; otherwise roll back.
- Cancellation rejection is one Rust-owned write transaction: require and change exactly one `pending` review to `rejected`, set `resolved_at`, do not change parent status, and commit only after that exact mutation succeeds.
- Cross-table cardinality, service/kind compatibility, status transition, occupancy, conflict, and category-dependent location rules remain Rust-side. No trigger, stored procedure, or generic maintenance abstraction substitutes for them.

### STILL UNIMPLEMENTED

This approval creates no business table, executable SQL file, migration, migration SQL, writable connection policy, foreign-key PRAGMA, transaction API, Rust business type, IPC, form, or workflow. The existing production schema version 1 bootstrap remains unchanged and need not become `STRICT`. This exact physical contract is assigned `database_schema_version = 2`, with `metadata_contract_version = 1`, SQLite `user_version = 2`, unchanged `application_id = 0x43484150`, and unchanged `ApplicationDatabaseFormatIdentity`. The only compatibility direction is 1 -> 2; versions newer than 2 are unsupported and downgrade-refused, and there is no generic unsupported-to-2 rule. Version assignment alone does not create migration eligibility or authorization, does not change migration-confirmation code, and does not implement version 2.
