# Architecture

Vite serves and bundles the TypeScript React presentation. React Router supplies four explicit placeholder routes and an unknown-route fallback. The Tauri command bridge exposes one `health_check` operation. Rust constructs its typed, non-sensitive response and owns the desktop runtime.

React may render UI, navigate placeholders, and request health. Privileged operations belong in Rust. React must never directly access a future database, filesystem, encryption key, or privileged service.

The current structure is deliberately small: `src/` contains shell code and frontend tests; `src-tauri/` contains Tauri configuration, one capability, Rust entry points, the command, Rust-owned storage and database trust-boundary foundations, the Windows production SQLCipher dependency, a private Windows-only raw-key application primitive, and Rust tests; `docs/` contains constraints; and `.github/workflows/ci.yml` contains Windows-only validation.

Rust owns production path resolution. Tauri's Rust-side local application-data resolver supplies the application-owned per-user directory associated with `io.github.cltubigon.churchapp`; Rust appends the single fixed filename `parish-data.db`. Production, development, automated-test, and restore-staging paths have distinct wrapper types and separate resolvers. Development uses an explicitly non-production identity, automated tests require a unique safe test identifier beneath an injected temporary root, and restore staging cannot be used as an active production path.

No Tauri command accepts or returns a database or filesystem path. React cannot select, override, supply, or receive the production location. Path construction performs no filesystem operations, and normal startup does not resolve, inspect, create, or open production storage in this stage.

Canonical persistence naming remains in `storage_foundation`: the existing `PRODUCTION_DATABASE_FILENAME` continues to own `parish-data.db`, while crate-private constants own `parish-data.db.stage`, `installation-evidence`, and the exact active and staged key/evidence wrapper names. Crate-private redacted wrapper types represent the evidence directory, active and staged wrappers, and staged database. One aggregate joins all paths beneath a caller-supplied synthetic root only. Evidence wrappers are always beneath `installation-evidence`; database publication staging is directly beneath the root and remains distinct from the existing restore-staging path. This construction does not call a Tauri resolver or any filesystem API.

`installation_evidence_persistence` adds a bounded helper over an already-supplied `std::io::Read`. It rejects lengths below 15 or above 65,550 before exact-size allocation, reads exactly the validated length with safe `Interrupted` retries, reports premature EOF coarsely, and performs one bounded single-byte read to reject trailing or growth data. It retains no native I/O error and exposes neither contents nor observed lengths through `Debug`; it does not parse, authenticate, or locate a wrapper.

The same module models path-free persisted-presence facts. A production root is validated, unexpectedly typed, or unavailable; each fixed file is absent, a regular file, unexpectedly typed, or unavailable; and the evidence directory is absent, a validated directory with four fixed child facts, unexpectedly typed, or unavailable. The pure classifier gives unavailable facts highest precedence, then unexpected types, then any staging, followed by complete active, external evidence without database, partial active, inconsistent database-only, and conclusive clean absence. `CleanAbsenceCandidate` grants no setup authority, and an absent evidence directory means only that its four fixed children are conclusively absent in the supplied facts.

Pure publication state machines encode three candidate workflows. Initial publication stages database, key, then evidence; reload-verifies all; publishes database, key, then evidence. Evidence-only replacement stages and reload-verifies evidence before replacing it. Key-generation replacement stages key then evidence, verifies both, and replaces key then evidence. Evidence is always the final success boundary. Refusal, staging failure, verification failure, publication failure, and interruption are terminal values; no cleanup, retry, resume, rollback, backup, timestamp, enumeration, or winner-selection transition exists. Every later attempt must begin from fresh supplied presence facts.

These persistence facts and publication states do not construct or convert to `installation_state::InstallationEvidence`. They establish no authentication, database correspondence, startup eligibility, setup authority, operational state, or real persistence behavior.

The crate-private Windows adapter is `installation_evidence_persistence/windows_filesystem.rs`, registered only by `#[cfg(windows)]`. Its accepted binding checks remain, and Windows tests now exercise one authentication-key-wrapper path beneath a unique test-owned temporary root. The sequence validates the opened `installation-evidence` directory, creates the exact stage name with `CREATE_NEW` and zero sharing, transfers the handle to one owner, writes exact bytes, calls `FlushFileBuffers`, closes, independently reopens with read-only sharing, obtains handle-reported size, uses the existing bounded reader, re-queries size, byte-compares, and calls the canonical protected-wrapper parser for object kind 1. It then calls `MoveFileExW(stage, active, MOVEFILE_WRITE_THROUGH)` without replacement or copy fallback, independently reopens and repeats active-file verification, confirms stage absence, and preserves an unrelated sentinel.

The separately scoped existing-file replacement proof remains inside that adapter's existing `#[cfg(test)]` module. It first creates the old active wrapper through the accepted no-replace proof and creates the replacement stage with the same create-new/write/flush/close discipline. Active and stage are independently reopened with restrictive read sharing and validated as regular non-reparse disk files, exact fixed normalized volume-GUID children, bounded exact bytes, and canonical authentication-key wrappers of kind 1. Handle information records both file IDs and volume serials; the evidence directory and both leaves must agree on volume and exact normalized directory. All ordinary active, stage, and directory handles are closed before `ReplaceFileW(active, stage, NULL, 0, NULL, NULL)`.

After the single call returns, pre-call assumptions are discarded. The proof freshly opens only the exact active and stage names and classifies absence, canonical old bytes, canonical replacement bytes, malformed or unexpected bytes, unexpected entry type, and unavailable inspection. The small test-only observation classifier distinguishes ordinary success, unchanged old-active/new-stage state, active-absent/new-stage partial state, reported-failure-but-completed state, and unexpected/unavailable state. A successful return is insufficient by itself: fresh active replacement bytes and canonical validity, exact final path, stage absence, stage-to-result file-ID continuity, old-active/result identity distinction, and sentinel preservation are all required. Deliberate sharing blockers are closed before fresh inspection, and the call is never retried.

Opened directories and files must report `FILE_TYPE_DISK`; files must not be directories or reparse points. Normalized final paths use `VOLUME_NAME_GUID`, reject UNC forms, and must equal the validated evidence-directory final path plus the exact fixed stage or active filename. Stage and active parents are also required to be the same typed test directory. This narrows risk in the proof but does not establish complete reparse, junction, path-race, or TOCTOU resistance.

The normal-tree hardening proof is a separate Windows-test-only inspection sequence. It opens the operating-system temporary-directory anchor, the unique root, one ordinary intermediate, and the exact `installation-evidence` directory independently with `OPEN_EXISTING`, backup semantics, and open-reparse-point semantics, then retains all four handles while validating an active or staged wrapper. Each directory must be a non-reparse disk directory with a zero tag, a normalized volume-GUID final path, an exact component boundary, and a `FILE_ID_INFO` identity. Directory identities are queried before and after the leaf read while the handles remain live.

For this proof, preferred identity is the 64-bit `FILE_ID_INFO.VolumeSerialNumber` plus all 128 bits of `FILE_ID_INFO.FileId`; the older file-index representation remains only in the unchanged publication/replacement regression code. UTF-16 final-path validation requires the `\\?\Volume{GUID}\` form, rejects UNC and malformed or oversized output, folds ASCII case only in the GUID hex digits, and compares every application-owned component with exact ordinal spelling. Parent and leaf volume serials and volume-GUID prefixes must agree.

Protected active and staged wrapper leaves alone require exactly one link. A leaf snapshot contains identity, size, attributes, reparse tag, link count, and final path before the existing bounded reader and canonical kind-1 parser run; every fact is queried again on the same handle afterward and any change fails closed. The deterministic policy seam covers changed identities, links, paths, volume facts, and unavailable reinspection without creating hostile filesystem objects. No directory or database hard-link rule is introduced.

This normal-tree evidence does not remove the remaining path-based publication races. The accepted initial-publication and replacement APIs and their handle-closure rules are unchanged; the hard-link and controlled exact-target substitution fixtures add only test evidence, while hostile reparse, broader directory substitution, local-volume, and hot-plug policy remain separate future work.

The Windows-test-only hard-link fixture extends that evidence without adding a callable production operation. Separate active and staged cases create one canonical kind-1 wrapper beneath `synthetic-component/installation-evidence`, observe one initial link, and use only `std::fs::hard_link` to create `wrapper-hard-link-alias.synthetic`. The approved name and alias must share the complete volume serial and 128-bit file ID plus byte-identical canonical content while retaining distinct normalized final paths. Exact-name validation rejects the alias, and the existing hardening path rejects the approved name at two links before its injected mutation or bounded-reader closures can run. Removing only the alias must restore the approved name to one link with unchanged identity and bytes. No publication or replacement function runs in these cases.

The separate Windows-test-only evidence-directory substitution fixture targets only `ordinary-component/installation-evidence`. It retains the temporary-directory anchor, unique root, intermediate, and a read-access evidence-directory handle opened without delete sharing. With wrapper and temporary inspection handles closed, `std::fs::rename` refuses to move the target and fresh inspection confirms unchanged full identity, exact normalized path, candidate identity/path, independently bounded canonical wrapper bytes, retained ancestors, and sentinel. The target and every descendant or duplicate handle then close while the temporary/root/intermediate handles remain retained. Exactly two synthetic renames move the original to `evidence-displaced.synthetic` and `substitute-candidate.synthetic` into exact `installation-evidence`.

Fresh post-substitution opens show the displaced directory retains the saved original full identity and exact displaced path, while the exact evidence path has the saved candidate identity and a byte-identical canonical authentication-key wrapper. The exact-path identity differs from the saved original identity, so identity mismatch is decisive despite exact path and equal bytes. The test-only continuity classifier reports substitution and does not invoke its publication, replacement, or wrapper-mutation continuation. This is one controlled case only: residual path-based races, hostile concurrency, intermediate/root substitution, and production enforcement remain unresolved.

The retained evidence-directory replacement compatibility proof is another Windows-test-only case. After creating the old active through the accepted initial-publication path and the stage through create-new/write/flush/close, it opens only the exact evidence directory for retention with `GENERIC_READ`, `FILE_SHARE_READ | FILE_SHARE_WRITE`, no delete sharing, `OPEN_EXISTING`, backup semantics, and open-reparse-point semantics. The synthetic parent is observed only long enough to validate the directory's exact component and volume relationship; no temporary, root, intermediate, active, or staged handle spans replacement. Active and stage are independently validated by the accepted preflight, and every leaf handle closes before the call.

The same retained handle is queried immediately before and immediately after the unchanged `ReplaceFileW(active, stage, NULL, 0, NULL, NULL)` call and again after fresh exact-name child inspection. Each boundary requires unchanged full directory `FILE_ID_INFO`, normalized volume-GUID final path, disk-directory and reparse facts, exact component relationship, and saved-parent volume relationship. Fresh child inspection runs while that parent handle remains open and reuses the existing replacement classifier; normal completion still requires canonical new bytes at active, stage absence, exact active path, staged/result identity continuity, and old/result identity difference. This narrows ordinary same-operation directory-substitution exposure but does not make the child operation handle-relative or remove child-entry, cross-process, or other TOCTOU races.

The local-volume candidate proof is private to the existing Windows test module. It starts from one retained, disk-backed, non-reparse directory handle for a unique test root and reuses the bounded `FILE_NAME_NORMALIZED | VOLUME_NAME_GUID` query and strict GUID-prefix validation. The exact first 49 UTF-16 units form the derived `\\?\Volume{GUID}\` root; one terminating NUL is appended only for one `GetDriveTypeW` call. Coarse path and drive facts yield only candidate, rejected, or unavailable outcomes. Fixed plus strict GUID evidence produces only `LocalFixedCandidate`; it has no conversion into installation, setup, startup, persistence, publication, replacement, or database authority.

The private nested device-property proof supplements that prerequisite without changing it. It retains the validated test-root handle, removes exactly the final separator from the strict 49-unit root, appends one NUL, and opens that volume device once with desired access zero, read/write sharing, `OPEN_EXISTING`, and flags zero. It submits one fully initialized `StorageDeviceProperty`/`PropertyStandardQuery` first into an exact `STORAGE_DESCRIPTOR_HEADER` buffer and then into an exactly sized zeroed buffer capped at 65,536 bytes. The parser reads raw byte slices only: exact compiled layout version, stable bounded size, the removable byte, bus type, and bounds for nonzero string offsets that are never followed. It performs no structure cast and decodes or reports no device string or identifier.

Only accepted `LocalFixedCandidate`, a strict non-removable descriptor, and an approved candidate bus family can yield private non-authoritative `DevicePropertyCandidate`. Removable media rejects; virtual, file-backed virtual, iSCSI, Fibre, and Spaces remain unresolved; USB, 1394, SD, MMC, SCSI, and RAID require controlled-host review; every other value fails closed. The proof performs exactly two storage-property IOCTL calls and no hot-plug query. Driver-reported device properties do not establish device non-removability, non-hot-plug or surprise-removal behavior, internal placement, physical locality, absence of virtual/profile/remote backing, durability, or production suitability. It does not resolve Church App production storage or convert into any authority-bearing type.

Only Windows tests create filesystem state. Each test creates exactly one unique root beneath the operating-system temporary directory, its required synthetic children, one sentinel, and the files needed by that case. Successful tests remove that exact root; failure unwinding attempts at most one best-effort root-only removal without replacing the original failure. This teardown is not production stale-stage cleanup or repair.

Rust also owns a narrow initialization decision boundary. `InstallationEvidence` distinguishes never initialized, initialized with expected storage present or missing, inconsistent evidence, and unavailable evidence. Ordinary startup supplies no setup authorization: never-initialized remains setup-required, initialized-and-present indicates only future open eligibility, and initialized-but-missing, inconsistent, or unavailable evidence fails closed.

First-time setup authorization is a separate in-memory Rust transition with a private-field authorization type. It can be produced only after the dedicated transition accepts never-initialized evidence; raw frontend values cannot construct it. Installation evidence, setup authorization, and future storage opening remain separate. This stage does not inspect the real filesystem, persist evidence, perform setup, resolve a production path during startup, or create or open storage. No frontend or Tauri IPC operation has setup authority.

Rust now also owns a platform-neutral logical installation-evidence contract. Its fields are grouped by purpose:

- authoritative identity inputs for future cross-checking: permanent application identifier, application database-format identity, and immutable parish identifier;
- cross-check fields: installation identifier, database-key generation identifier, and setup publication identifier;
- lineage fields: installation generation and recovery or replacement generation, both with 1 as the initial valid committed generation and zero rejected;
- non-authoritative format and metadata fields: evidence-format identity, evidence-format version, and creation timestamp represented as nonzero UTC seconds since the Unix epoch.

The raw-to-typed constructor validates only current format identity and version, canonical application and database-format identities, canonical parish-identifier syntax, nonzero fixed-size opaque identifiers, nonzero generations, and a nonzero timestamp. A `StructurallyValidatedInstallationEvidence` value therefore means only structurally valid and locally coherent under the current contract. It is explicitly distinct from future authenticated evidence, future database-cross-checked evidence, and the current operational `installation_state::InstallationEvidence`. There is no conversion between those types in this stage.

Serialization is limited to one canonical version-1 plaintext encoder whose only input is `StructurallyValidatedInstallationEvidence`. It returns a fixed 164-byte value: magic at `0..8`, encoding version at `8..10`, payload length at `10..12`, evidence-format identity at `12..28`, logical evidence-format version at `28..30`, application-identifier length at byte `30`, the exact application identifier at `31..60`, database-format identity at `60..76`, parish identity at `76..92`, installation identity at `92..108`, installation generation at `108..116`, recovery or replacement generation at `116..124`, database-key generation identity at `124..140`, setup publication identity at `140..156`, and creation timestamp at `156..164`. The payload length is 152 (`00 98`). All multi-byte integers are unsigned big-endian, and identities are raw 16-byte values. There is no padding, reserved area, extension area, or trailing data.

The encoder writes each field explicitly and deterministically. It does not authenticate bytes, establish operational authority, or convert the structural contract into `installation_state::InstallationEvidence`.

The parsing flow is `&[u8]` raw bytes → strict version-1 parser → `ParsedUntrustedInstallationEvidenceContract` → explicit structural validation → `StructurallyValidatedInstallationEvidence`. The parser rejects any total length other than 164 before field decoding, then checks the exact eight-byte magic, unsigned big-endian encoding version 1, unsigned big-endian payload length 152, application-identifier length 29, and valid UTF-8 in the fixed 29-byte application-identifier field. It decodes every remaining field from its fixed offset without padding, extension, trailing-byte acceptance, scanning, guessing, fallback, or normalization.

The approved outer authenticated-envelope framing is exactly 226 bytes: `CHEVAUTH` magic at `0..8`; unsigned big-endian envelope version 1 at `8..10`; unsigned big-endian authentication algorithm identifier 1 at `10..12`; a distinct nonzero 16-byte evidence-authentication-key generation identifier at `12..28`; unsigned big-endian plaintext length 164 at `28..30`; the exact unchanged canonical plaintext at `30..194`; and a complete 32-byte HMAC-SHA-256 tag at `194..226`. The authentication-input prefix is exactly `0..194`. There is no nonce, salt, padding, reserved field, extension area, negotiation, fallback, or trailing data.

Construction accepts only an existing canonical `EncodedInstallationEvidence`, a nonzero authentication-key generation identifier, and a caller-supplied `EvidenceAuthenticationKey`. It writes the fixed prefix, computes `Hmac<Sha256>` over exact bytes `0..194`, and copies the complete 32-byte tag to `194..226`. Trusted construction can produce both the encoded envelope and a private `CryptographicallyAuthenticatedEnvelopeV1`.

Verification follows `&[u8]` raw bytes → strict framing parser → `ParsedUntrustedAuthenticatedEnvelopeV1` → HMAC verification → `CryptographicallyAuthenticatedEnvelopeV1`. The parsed untrusted type retains the exact prefix bytes, and verification uses those bytes without parsing, reconstructing, or normalizing the inner plaintext. The cryptographically authenticated type retains the HMAC-covered generation identifier but cannot release plaintext. Only a successful generation-identifier match produces `GenerationMatchedAuthenticatedEnvelopeV1`, which can release the exact 164 bytes to the existing plaintext parser. That parser still returns `ParsedUntrustedInstallationEvidenceContract`, and structural validation remains a later explicit transition. No conversion to operational `installation_state::InstallationEvidence` exists.

The separate `EvidenceAuthenticationKey` type owns exactly 32 bytes passed into its Rust ownership boundary, including bytes moved from the production generator. It is distinct from the evidence-authentication-key generation identifier, database-key generation identifier, and authenticated-envelope framing. Its private bytes are exposed through a crate-private closure only long enough to initialize HMAC state; authenticated results retain no key.

Authentication-material generation is a separate crate-private transition: `getrandom::fill` requests exactly 32 bytes into a caller-owned buffer that moves directly into `EvidenceAuthenticationKey`, then a separate `getrandom::fill` requests exactly 16 bytes for the existing `EvidenceAuthenticationKeyGenerationIdentifier` validation boundary. An all-zero identifier is retried with a fresh identifier-only fill, with three total identifier attempts. Randomness failure or three zero identifiers fails closed. The redacted result owns only the key and identifier and has no production caller. Generation does not invoke HMAC construction and remains separate from DPAPI, persistence, setup, startup, database cross-checking, active-generation policy, and operational installation state.

Malformed encoding returns `InstallationEvidenceParseError`; well-framed but logically invalid fields parse successfully and later return `ContractValidationError` through the existing validation rules. Parsed fields are private and remain untrusted. Neither parsed nor structurally validated evidence converts to operational `installation_state::InstallationEvidence`.

Dependency-free deterministic malformed-input tests exercise every byte position, framing and field boundaries, wrong lengths, representative byte patterns, and selected two-byte framing changes. Any mutated input that parses and remains structurally valid must re-encode byte-identically. This is testing evidence for parser behavior and canonicality, not authentication or a security proof.

Windows in-memory protection adds one outer wrapper for opaque DPAPI output. Version 1 is exactly a 14-byte header plus the blob: `CHDPAPI\0` at `0..8`, wrapper version 1 at byte `8`, protected-object kind at byte `9` (`1` for authentication material and `2` for authenticated evidence), an unsigned big-endian `u32` blob length at `10..14`, and the exact opaque bytes at `14..`. The blob must be nonempty and no longer than 65,536 bytes; the total wrapper is therefore capped at 65,550 bytes. Parsing requires an exact declared length and rejects unknown versions, kinds, mismatches, and trailing data before allocation.

The protected authentication-key plaintext is exactly 49 bytes: payload version 1 at byte `0`, the nonzero 16-byte evidence-authentication-key generation identifier at `1..17`, and the exact 32-byte key at `17..49`. It has no magic, key-length field, padding, reserved area, or extension data. Key payload and authenticated evidence are protected separately.

The recovery flow is key first: validate the key wrapper, DPAPI-unprotect candidate key bytes, validate the fixed payload, then validate and DPAPI-unprotect the evidence wrapper. Strict envelope framing and HMAC verification precede comparison of the HMAC-covered generation identifier with the identifier recovered inside DPAPI. Only `GenerationMatchedAuthenticatedEnvelopeV1` can release plaintext to the existing parser; structural validation remains a separate later transition.

All DPAPI unsafe code remains confined to the Windows current-user DPAPI adapter. It hard-codes UI-forbidden current-user calls with null entropy, description, reserved, and prompt pointers. Successful native output is validated and copied before release; unprotected native output is best-effort zeroized before its single `LocalFree`. Filesystem unsafe code is separately confined to the Windows filesystem adapter. Neither boundary maps results into setup, startup, IPC, frontend, database, or installation-state authority.

Authenticated-envelope hardening deterministically mutates every one of the 226 byte positions and classifies strict framing failures separately from HMAC authentication failures. Header mutations follow the existing framing rules; framing-preserving authentication-key generation identifier and plaintext mutations must fail authentication, and every terminal-tag mutation must parse as framing and then fail authentication. Wrong-key, wrong-length, pattern, boundary, and selected cross-boundary two-byte corpora exercise the same chain without randomness or side effects.

DPAPI malformed-input hardening deterministically covers every byte of the fixed wrapper header and protected-key payload, bounded declared-length, truncation, trailing-data, pattern, boundary, fake-protector, and opaque-blob corpora, plus first, midpoint, and final-byte corruption of real protected key and evidence blobs. DPAPI-unprotected output remains candidate data until strict payload or envelope framing, HMAC, generation, plaintext, and structural validation succeeds. Parsing a protected-key payload establishes only candidate key material, not HMAC authority. These tests do not change either protected format, any production API, or the established trust boundaries.

Tests also deliberately recompute valid tags over malformed inner plaintext. Those envelopes authenticate successfully but then fail the existing plaintext parser or structural-validation boundary, demonstrating that authentication and logical validity are separate. An alternate canonical plaintext completes authentication, parsing, structural validation, and byte-identical re-encoding. This hardening provides neither replay nor rollback protection.

The contract and HMAC transitions themselves perform no randomness, persistence, loading, filesystem or registry access, DPAPI, database access, startup integration, setup authorization, or Tauri IPC. The separate in-memory DPAPI layer wraps the authenticated envelope. Database-first and evidence-last multi-file publication ordering remains represented only by the pure state machines; the temporary runtime proof covers only one wrapper and must not be treated as that sequence.

Future encrypted local parish data is intended to be authoritative, while central services are non-authoritative. The future public web application and canonical contracts are separate repositories. No interfaces, ports, adapters, schemas, clients, or placeholders for those systems exist here.

Production installation-evidence filesystem inspection, persistence, loading, publication, replacement, database cross-checking, rollback protection, and supersession handling; production evidence-root resolution; setup orchestration; database creation and opening; schemas and migrations; user authentication; recovery; and product workflows remain deferred. The temporary proofs establish visible correctness for one synthetic wrapper on the observed Windows filesystem, not directory-entry or volume flush durability after power loss, ACL or metadata preservation, named-stream behavior, backup, cross-volume behavior, production storage authority, multi-file database-first/evidence-last publication, complete path-race resistance, or runtime replacement detection. Special failure-family simulation proves only deterministic classifier behavior, not occurrence of those native states on the host.

The layers remain deliberately separate: filesystem and sidecar inspection; connection-lifetime guarding; trusted key recovery; guarded connection opening; raw-key application; SQLite/SQLCipher readability and integrity validation; live metadata/header observation and decoding; correspondence; freshness; installation-state classification; startup authorization; operational opening; and separately authorized setup, migration, rekey, restore, recovery, replacement, and destructive cleanup. The implemented chain currently ends at `LiveMetadataAndHeaderValidatedProductionDatabaseConnection`, before database/evidence correspondence. No earlier value or stage grants later authority.

SQLCipher Community Edition is the selected engine for production parish databases, production backups, and production recovery databases; plain SQLite is prohibited for those artifacts. Windows production depends on exactly `rusqlite = { version = "=0.39.0", default-features = false, features = ["bundled-sqlcipher-vendored-openssl"] }` under `[target.'cfg(windows)'.dependencies]`, without a Windows `rusqlite` development dependency or direct `libsqlite3-sys` dependency. The private Windows-only `sqlcipher_database_key_application` module still owns only the raw-key submission transition. The guarded handoff is its sole application-level caller and passes only `&GenerationBoundDatabaseKey` plus the already-open connection handle. The primitive encodes the key in one fixed 67-byte owner as lowercase `x'<64 hex characters>'`, calls `sqlite3_key` exactly once, treats only `SQLITE_OK` as success, best-effort clears its owned encoded bytes, and collapses failure to `DatabaseKeyApplicationError::Failed`. Neither the primitive nor the handoff exposes a public command, frontend, or IPC surface.

The exact ownership chain is `ProductionDatabasePath` -> `InspectedProductionDatabaseFile` -> private `ConnectionLifetimeWriteGuard` -> `rusqlite::Connection`, with `GenerationBoundDatabaseKey` borrowed only for the one key application, followed by an opaque keyed-but-unvalidated owner, an opaque readability-and-integrity-validated owner, and an opaque live-metadata-and-header-validated owner. All three owners retain the inspected proof, guard, and connection as one lifetime unit; the final owner additionally retains one owned `DatabaseMetadataContractV1`. No guard handle, file, path, identity, content-read API, raw Windows handle, raw SQLite handle, or database-content capability escapes. Key success does not establish key correctness, readability, or integrity; readability/integrity success does not establish metadata or header validity; live metadata/header success establishes neither correspondence, freshness, nor startup authorization.

The exact implemented order is:

1. Receive the existing successful metadata-only `InspectedProductionDatabaseFile` proof.
2. Acquire the private `ConnectionLifetimeWriteGuard` with `FILE_READ_ATTRIBUTES | FILE_READ_DATA`, `FILE_SHARE_READ`, `OPEN_EXISTING`, and `FILE_FLAG_OPEN_REPARSE_POINT`.
3. Identity-match the guard to the inspected database proof.
4. Perform exactly one application-level path-based `Connection::open_with_flags_and_vfs(..., "win32")` call using `SQLITE_OPEN_READ_ONLY | SQLITE_OPEN_FULL_MUTEX | SQLITE_OPEN_PRIVATE_CACHE | SQLITE_OPEN_NOFOLLOW` and no read-write, create, shared-cache, no-mutex, memory, or URI flag.
5. Retrieve SQLite's borrowed main-database Windows handle through `SQLITE_FCNTL_WIN32_GET_HANDLE` and identity-match it to the same inspected proof.
6. Apply the pre-key policy: five-second busy timeout; extension loading disabled; defensive mode enabled; trusted schema disabled; no-checkpoint-on-close enabled; attach-create and attach-write disabled; and the main database confirmed read-only.
7. Apply the existing `GenerationBoundDatabaseKey` exactly once.
8. Enable and verify query-only only after key application.
9. Return the opaque keyed-but-unvalidated owner.

The connection, guard, and inspection proof form one lifetime unit. They remain together after a normal close failure or a construction-time close failure, and the API exposes only consuming close or close-retry transitions. There is no operational caller.

The supported production baseline is Windows 10 x64 and Windows 11 x64, local NTFS, a non-elevated standard user, and CurrentUser DPAPI. Windows ARM64, 32-bit Windows, ReFS, removable and network storage, Wine, Windows Server, and compatibility layers remain unsupported until separately approved.

### Key separation

The database key is an independent random 256-bit value generated from the Windows OS cryptographic RNG. It is never password-derived or derived from parish, installation, evidence, device, or user values, and it is never shared with the evidence HMAC key. Its owner is non-`Copy`, exposes no unrestricted `Clone`, redacts formatting, and best-effort zeroizes owned buffers. A dedicated CurrentUser-DPAPI wrapper protects the live database key. Portable recovery instead uses a separate random recovery key and authenticated recovery envelope. Recovery-key custody, duplication, rotation, loss, and destruction are explicit operator/security responsibilities.

### Metadata version 1

The singleton table is named `church_app_database_metadata` and contains exactly one canonical, non-null row. Missing, duplicate, partial, wrong-storage-class, wrong-length, unsupported, or malformed state fails closed.

| Field | Approved SQLite representation and rule |
| --- | --- |
| `singleton_id` | `INTEGER`; canonical value 1 |
| `metadata_contract_version` | positive `INTEGER`; initial value 1 |
| `database_schema_version` | positive `INTEGER`; initial value 1 |
| `permanent_application_identifier` | bounded canonical UTF-8 `TEXT`; exactly `io.github.cltubigon.churchapp` |
| `database_format_identity` | existing typed `ApplicationDatabaseFormatIdentity`; `BLOB`; exactly 16 bytes; direct typed decoding; exact typed equality; never text |
| `parish_identifier` | `BLOB`; exactly 16 bytes |
| `installation_identifier` | `BLOB`; exactly 16 bytes |
| `installation_generation` | `BLOB`; exactly 8-byte big-endian encoding |
| `recovery_replacement_generation` | `BLOB`; exactly 8-byte big-endian encoding |
| `database_key_generation_identifier` | `BLOB`; exactly 16 bytes |
| `setup_publication_identifier` | `BLOB`; exactly 16 bytes |
| `database_created_at` | non-negative UTC Unix milliseconds in `INTEGER`; diagnostic only |

The database-format identity is never UTF-8, hex, UUID text, Base64, a numeric reinterpretation, alternate spelling, hash, prefix, or fingerprint. SQLite `application_id` is `0x43484150`. SQLite `user_version` mirrors `database_schema_version`, while metadata remains authoritative. A wrong fixed application ID, unsupported correctly represented metadata version, malformed representation, and supported metadata/user-version disagreement have distinct fail-closed categories under the implemented live-observation boundary; no state is auto-repaired.

### Correspondence, freshness, and authority

Exact typed equality is required across database and evidence for the permanent application identifier, `ApplicationDatabaseFormatIdentity`, parish identifier, installation identifier, database-key generation identifier, and setup-publication identifier. Lineage comparison applies to installation generation and recovery/replacement generation. Evidence format identity and evidence format version remain evidence-only. Timestamps are diagnostic and never authorize freshness.

A future separate CurrentUser-DPAPI-protected freshness anchor records installation identifier, installation generation, recovery/replacement generation, database-key generation identifier, and setup-publication identifier. Normal startup eventually requires database, evidence, and anchor agreement: equal lineage succeeds; lower evidence is stale evidence; higher evidence is a stale database; opposing lineage movement is rollback suspicion; ambiguity fails closed. A coordinated rollback of every local artifact and applicable profile state to one mutually consistent snapshot is not detectable by this design, so it provides no cryptographic monotonic rollback guarantee.

Setup is the only creation authority. Ordinary startup never creates a database, key wrapper, evidence, anchor, metadata, or sidecar. Recovery, restore, migration, rekey, anchor replacement, database replacement, and destructive cleanup require separate explicit authorization. There is no generic repair authority.

### Opening, integrity, storage, and migrations

Production database-file inspection remains metadata-only and separate from the guard. The guard deliberately has native file content-read access for connection lifetime compatibility, but exposes no content-read API. The accepted open is read-only and no-create for the main database file, bounded to one application-level path open, and has no application retry loop or writable fallback; SQLite internal retries remain engine behavior. Later SQLite operations may still involve auxiliary-file behavior. `SQLITE_OPEN_NOFOLLOW` is defense in depth and not the primary Windows reparse guarantee; query-only is defense in depth and not the primary read-only guarantee. No `immutable=1` or URI open is used.

While the verified guard remains open, ordinary Windows filesystem opens requesting incompatible write or delete access to the guarded file object are refused under normal Windows sharing semantics. This bounded guarantee does not cover pre-guard mutation, kernel-mode activity, filesystem filters, raw-volume access, privileged bypass, storage or hardware faults, or operating-system/filesystem defects.

The implemented and accepted readability-and-integrity transition consumes `ProductionReadOnlyDatabaseConnection` and uses its same privately owned connection sequentially. It runs exactly `PRAGMA cipher_integrity_check`, requires normal end-of-stream with zero rows, then runs exactly `PRAGMA main.quick_check(1)`, requires exactly one SQLite `TEXT` row whose complete value is exactly `ok`, and requires normal end-of-stream after that row. No separate readability query exists: the limited quick check is the SQLite readability boundary. This stage does not read `sqlite_master`, metadata tables, `application_id`, `user_version`, product tables, or arbitrary content and exposes no unrestricted SQL.

The cipher row contract is asymmetric. Normal zero-row completion is success. The first returned row is sufficient to establish `EncryptedDatabaseAuthenticationOrCipherIntegrityFailed`; its diagnostic text is not decoded, copied, formatted, retained, or logged, later rows need not be consumed, and the row stream must be dropped or reset before close. Stopping after that first row is not incomplete success because failure is already established. Any cipher statement error, interruption, malformed completion, or premature termination fails closed rather than establishing success.

For `PRAGMA main.quick_check(1)`, zero rows, multiple rows, a non-text value, a text value other than exact `ok`, a stepping error, interruption, malformed shape, or premature termination fails closed. Diagnostic text never crosses the boundary. This limited quick check is not full `integrity_check` and does not prove every SQLite invariant. Full integrity checking remains reserved for controlled backup acceptance, staged restore, migration, rekey/key replacement, journal recovery, database replacement, explicit diagnostics, and abnormal-interruption recovery.

Both checks retain the existing `ConnectionLifetimeWriteGuard` and `InspectedProductionDatabaseFile`; query-only, defensive mode, and read-only opening remain active. No explicit SQLite transaction is added, and no stronger snapshot guarantee is claimed beyond the guarded same-connection lifetime. No active cancellation API or rusqlite hooks feature is part of this stage. `SQLITE_INTERRUPT`, statement errors, malformed result shape, and premature termination map to fail-closed coarse outcomes, and active user cancellation remains separately scoped.

Success is represented only by possession of a new opaque readability-and-integrity-validated production connection owner. The consuming type transition moves the same `rusqlite::Connection`, guard, and inspection proof into that owner, which exposes only consuming explicit close and later separately approved fixed consuming transitions. It establishes no metadata table existence, metadata row validity, SQLite `application_id`, SQLite `user_version`, schema-contract validity, database/evidence correspondence, freshness, startup/setup authority, migration authority, recovery authority, backup/restore authority, or operational database use, and exposes no connection reference, arbitrary-SQL closure, raw handle, path, or identity.

The canonical validation failure categories are `EncryptedDatabaseAuthenticationOrCipherIntegrityFailed`, `SQLiteReadabilityOrIntegrityFailed`, `ValidationUnavailable`, and `ValidationInterruptedOrIncomplete`. If validation fails, all statement and row-stream borrows are released and explicit close is attempted. A successful close returns the primary coarse validation category. A close failure preserves both that category and an opaque consuming close-retry owner containing the complete connection/guard/inspection-proof lifetime unit; retry failure retains the same unit and category again. SQL or PRAGMA text, result diagnostics, paths, keys, identifiers or identities, SQLite/native codes, raw handles, and rusqlite errors or chains are never retained or exposed.

`cipher_integrity_check` may perform a synchronous whole-file scan with work proportional to database pages. This stage adds no production database-size ceiling and promises neither bounded latency nor active cancellation. That is accepted only because the validation boundary has no operational caller. Operational integration must later define database-size limits, execution-time expectations, responsiveness, and cancellation policy.

The exact application-owned production directory and filename `parish-data.db` are required on local NTFS. Reparse points, symlinks, junctions, mount traversal, cloud placeholders, hard links, network paths, removable storage, unstable final path/file identity, and unexpected sidecars fail closed. Database-aware race protection and a dedicated database hardening adapter are required; the evidence-wrapper loader cannot simply be reused. WAL and SHM are initially prohibited. Startup never deletes or repairs sidecars.

Transactions use rollback-journal `DELETE`, `synchronous=FULL`, explicit transactions, `secure_delete=ON`, and `auto_vacuum=NONE`. There is no automatic journal-mode switch, VACUUM, or WAL checkpoint policy. Rust owns forward-only migrations. Ordinary startup may detect but never execute a migration. Migration requires explicit maintenance authorization, a verified recoverable backup, and successful full integrity checking; interruption fails closed and a newer unsupported schema is never automatically downgraded.

Coarse errors outside this validation stage remain separately scoped. Within this stage the only primary categories are `EncryptedDatabaseAuthenticationOrCipherIntegrityFailed`, `SQLiteReadabilityOrIntegrityFailed`, `ValidationUnavailable`, and `ValidationInterruptedOrIncomplete`; wrong key versus cipher-page corruption and corrupt versus unsupported SQLite content are intentionally not split. Later metadata, correspondence, freshness, sidecar, and operational errors remain separate. No error exposes a path, SQL or PRAGMA text, result diagnostic, key, identifier or identity, generation, metadata value, DPAPI data, native status, raw handle, raw error chain, username, or profile directory.

### Implemented live metadata and header validation

The implemented transition consumes `ReadabilityAndIntegrityValidatedProductionDatabaseConnection` and uses only fixed operations on its same privately retained connection. It first prepares and fully observes `PRAGMA main.application_id`, requiring one result column, exactly one row, SQLite `INTEGER`, signed-32-bit representability, and normal terminal end-of-stream. It then compares with `0x43484150` and stops immediately with `WrongApplicationId` on mismatch. Only after that success does it prepare and fully observe `PRAGMA main.user_version` under the same strict result-shape policy, retaining the signed value temporarily.

It then prepares and executes exactly:

```sql
SELECT
    singleton_id,
    metadata_contract_version,
    database_schema_version,
    permanent_application_identifier,
    database_format_identity,
    parish_identifier,
    installation_identifier,
    installation_generation,
    recovery_replacement_generation,
    database_key_generation_identifier,
    setup_publication_identifier,
    database_created_at
FROM main.church_app_database_metadata
LIMIT 2
```

The metadata statement must expose exactly 12 result columns. Normal completion with no first row is `MetadataRowMissing`. The adapter copies the first row's 12 values into one private owned raw observation before stepping again because live row references must not outlive their row-stream step. A second row is `DuplicateMetadataRows`; normal end after the first proves exactly one row; a stepping failure is `MetadataObservationInterruptedOrIncomplete`. Fixed `LIMIT 2` distinguishes zero, exactly one, and more than one row without unbounded enumeration. The query does not filter on `singleton_id = 1`, because such a predicate could hide additional noncanonical rows.

The adapter preserves exact SQLite storage classes without casts or `typeof()`: `INTEGER` maps to `Integer(i64)`; `TEXT` undergoes strict UTF-8 validation before `Text(&str)`; `BLOB` maps to `Blob(&[u8])`; `NULL` maps to `Null`; and `REAL` is `MalformedMetadata`. The adapter constructs exactly one `RawDatabaseMetadataRow`, calls its existing `parse()` exactly once, calls `validate_structure()` exactly once, and does not duplicate pure field validation. It finally compares the validated metadata `database_schema_version` with the observed `user_version`; equality returns opaque `LiveMetadataAndHeaderValidatedProductionDatabaseConnection`. No other query, PRAGMA, schema introspection, dynamic SQL, cast, `typeof()`, or arbitrary content access is approved.

The success owner privately retains the unchanged `ConnectionLifetimeOwner` and one owned `DatabaseMetadataContractV1`. The accepted application ID is fixed and the accepted user version duplicates the validated metadata schema version, so neither header value remains separately stored. The owner exposes only consuming explicit close and later separately approved fixed consuming transitions. It exposes no `Connection`, arbitrary SQL, callback over `Connection`, detachable proof, raw header, raw metadata observation, path, handle, identity, or diagnostic.

The implementation resides in the sealed private `live_metadata_and_header_validation` child module beneath `production_database_connection_handoff`. The private visibility of `ConnectionLifetimeOwner`, `Connection`, the guard, the inspection proof, and close helpers remains unchanged. It introduces no generic connection callback or crate-root sibling bridge.

On every primary failure, `Rows` and `Statement` are released before close, and temporary header values, owned raw observations, parsed metadata, and partially validated metadata are discarded. Explicit close success returns the primary category. Close failure retains that same category plus the complete connection/guard/inspection lifetime unit in an opaque consuming retry owner, and repeated failures preserve both. Explicit close of a successfully validated live-metadata owner first discards its metadata contract; if close fails, only the complete connection/guard/inspection lifetime unit remains in the close-retry owner.

Success proves only the two exact header observations, correct `application_id`, exactly one metadata row, exact storage-class representations, strict UTF-8, success of the existing pure parse and structural validation, `user_version` agreement with the supported metadata schema version, and continued ownership of the same guarded readability-and-integrity-validated connection. Production only reads the already-existing named relation. The stage validates no physical DDL, constraints, indexes, triggers, object kind, wider product schema, database/evidence correspondence, freshness, startup or operational authorization, setup completion, migration status, recovery, backup/restore suitability, replacement authority, business data, or operational opening. All of those later boundaries remain separately scoped, and `LiveMetadataAndHeaderValidatedProductionDatabaseConnection` has no operational caller.

Database/evidence correspondence is the next separately scoped boundary. It will compose `LiveMetadataAndHeaderValidatedProductionDatabaseConnection`, a trusted current installation-evidence input, and the existing pure correspondence foundation. The exact trusted input type, live taxonomy, mismatch precedence, success-owner contents, retention model, lineage handling, module placement, and test seams are not selected here.
